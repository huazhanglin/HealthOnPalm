# 健康智能体 App 技术架构审查报告

**审查人**: Senior Developer（高级开发工程师）
**审查时间**: 2026-07-17
**被审查文档**: `健康智能体App技术架构_20260708.md`
**审查结论**: **架构方向正确，但存在 4 个 P0 级问题（必须修复）、11 个 P1 级问题（建议修复）、8 个 P2 级建议**

---

## 一、总体评价

这份技术架构文档**框架完整、分层清晰**——Clean Architecture 分层（data/domain/presentation）、FastAPI 分模块结构、数据库表设计都到位。作为一个架构设计的起点，质量不错。

但从"可以直接指导编码"的标准来看，存在以下问题：
1. **部分代码有语法/逻辑错误**，直接复制会跑不起来
2. **安全设计缺失**——没有限流、异常信息直接暴露、没有安全存储方案
3. **LLM 对话核心链路缺失**——没有流式输出、没有 token 控制、没有重试降级
4. **合规设计缺失**——健康数据没有加密方案、没有软删除、没有授权版本追踪
5. **开发路线图过于激进**——9 周完成全部功能不现实（与可行性分析审核结论一致）

以下按严重程度分 P0/P1/P2 三级列出所有发现。

## 二、P0 级问题（必须修复，否则无法正常运行或存在安全风险）

### P0-1: SQL 语法错误 — INDEX 不能写在 CREATE TABLE 内

**位置**: 第四章 4.1，messages 表和 health_data 表

**问题**: 文档中在 `CREATE TABLE` 语句内部写了 `INDEX idx_xxx (...)`，这是 MySQL 语法，PostgreSQL 不支持。

**文档写法**:
```sql
CREATE TABLE messages (
    ...
    INDEX idx_user_created (user_id, created_at DESC)  -- PostgreSQL 不支持
);
```

**PostgreSQL 正确写法**:
```sql
CREATE TABLE messages (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    role VARCHAR(20) NOT NULL,
    content TEXT NOT NULL,
    intent VARCHAR(50),
    tokens_used INTEGER,
    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP
);

-- 索引单独创建
CREATE INDEX idx_messages_user_created ON messages (user_id, created_at DESC);
```

**影响范围**: messages 表、health_data 表均有此问题。

### P0-2: FastAPI Depends() 用法错误

**位置**: 第三章 3.3，chat.py 的 send_message 和 get_chat_history

**问题**: `chat_service: ChatService = Depends()` 直接传空调用。FastAPI 的 `Depends()` 需要传入一个可调用对象（工厂函数），不能传空。

**文档写法**:
```python
chat_service: ChatService = Depends()  # 错误：Depends() 空参数
```

**正确写法**:
```python
# 在 deps.py 中定义工厂函数
from app.services.chat_service import ChatService

def get_chat_service() -> ChatService:
    return ChatService()

# 在路由中使用
@router.post("/chat", response_model=MessageResponse)
async def send_message(
    request: MessageCreate,
    current_user = Depends(get_current_user),
    chat_service: ChatService = Depends(get_chat_service)  # 传入工厂函数
):
```

### P0-3: 异常信息直接暴露给客户端 — 安全漏洞

**位置**: 第三章 3.3，第 460 行

**问题**: `raise HTTPException(status_code=500, detail=str(e))` 将原始异常信息返回给客户端，可能泄露内部实现细节（数据库连接串、API key 片段、堆栈信息等）。

**文档写法**:
```python
except Exception as e:
    raise HTTPException(status_code=500, detail=str(e))  # 危险
```

**正确写法**:
```python
import logging
logger = logging.getLogger(__name__)

except Exception as e:
    logger.exception("Chat processing failed")  # 内部记录完整堆栈
    raise HTTPException(
        status_code=500,
        detail="服务暂时不可用，请稍后重试"  # 客户端只看到通用提示
    )
```

### P0-4: LLM 客户端缺少流式输出 — 严重影响用户体验

**位置**: 第三章 3.4，llm_client.py

**问题**: `generate()` 方法使用同步等待完整响应，但 LLM 生成一个回复通常需要 3-10 秒。用户在这期间看不到任何反馈，体验极差。现代 AI 对话产品都使用流式输出（SSE），让用户看到逐字生成效果。

**文档写法**: 等待完整 response 后一次性返回 `response.content[0].text`

**需要增加流式方法**:
```python
from anthropic import AsyncAnthropic
from typing import AsyncGenerator

class LLMClient:
    def __init__(self):
        self.claude_client = AsyncAnthropic(
            api_key=os.getenv("ANTHROPIC_API_KEY"),
            timeout=30.0,  # 增加超时配置
            max_retries=3   # SDK 内置重试
        )

    async def generate_stream(
        self,
        messages: List[Dict[str, str]],
        system_prompt: str,
        model: str = "claude-sonnet-4-20250514",
        max_tokens: int = 2048,
    ) -> AsyncGenerator[str, None]:
        """流式生成 — 逐 token 返回"""
        async with self.claude_client.messages.stream(
            model=model,
            max_tokens=max_tokens,
            system=system_prompt,
            messages=messages,
        ) as stream:
            async for text in stream.text_stream:
                yield text

    async def generate(self, messages, system_prompt, model, max_tokens, temperature):
        """非流式生成（保留用于不需要流式的场景）"""
        try:
            response = await self.claude_client.messages.create(
                model=model,
                max_tokens=max_tokens,
                system=system_prompt,
                messages=messages,
                temperature=temperature
            )
            return response.content[0].text
        except Exception as e:
            logger.exception("LLM generation failed")
            raise  # 由上层处理降级
```

**后端也需要增加 SSE 端点**:
```python
from fastapi.responses import StreamingResponse
import json

@router.post("/chat/stream")
async def send_message_stream(
    request: MessageCreate,
    current_user = Depends(get_current_user),
    chat_service: ChatService = Depends(get_chat_service)
):
    async def event_stream():
        try:
            async for chunk in chat_service.process_message_stream(
                user_id=current_user.id,
                message=request.message
            ):
                yield f"data: {json.dumps({'content': chunk})}\n\n"
            yield f"data: {json.dumps({'done': True})}\n\n"
        except Exception:
            yield f"data: {json.dumps({'error': '生成失败'})}\n\n"

    return StreamingResponse(event_stream(), media_type="text/event-stream")
```

### P1-2: 对话历史无截断 — 会超出 token 限制

**位置**: 第二章 2.3，`_buildHistory()` 方法

**问题**: 将所有历史消息发送给 LLM，对话超过 10-20 轮后会超出模型上下文窗口限制，导致 API 报错或成本飙升。

**修复**:
```dart
List<Map<String, String>> _buildHistory() {
    // 只取最近 10 条消息（约 5 轮对话）
    final recent = _messages.length > 10
        ? _messages.sublist(_messages.length - 10)
        : _messages;

    return recent.map((m) => {
        'role': m.role == MessageRole.user ? 'user' : 'assistant',
        'content': m.content,
    }).toList();
}
```

后端也应做 token 计数和截断，不信任客户端的限制。

### P1-3: 消息 ID 用毫秒时间戳 — 有碰撞风险

**位置**: 第二章 2.3，第 250、273 行

```dart
id: DateTime.now().millisecondsSinceEpoch.toString(),
```

如果用户快速连续发送消息，同一毫秒内会生成相同 ID。已引入 `uuid` 依赖，应使用：

```dart
id: const Uuid().v4(),
```

### P1-4: LLM 客户端缺少多模型支持

**位置**: 第三章 3.4

**问题**: 架构总览提到 Claude（主力）/ GPT-4（备用）/ DeepSeek（降级），但代码只初始化了 Claude 客户端。缺少故障切换逻辑。

**建议增加**:
```python
class LLMClient:
    def __init__(self):
        self.providers = {
            'claude': AsyncAnthropic(api_key=os.getenv("ANTHROPIC_API_KEY")),
            'deepseek': AsyncOpenAI(
                api_key=os.getenv("DEEPSEEK_API_KEY"),
                base_url="https://api.deepseek.com"
            ),
        }
        self.primary = 'claude'
        self.fallback = 'deepseek'

    async def generate(self, messages, system_prompt, **kwargs):
        try:
            return await self._call_claude(messages, system_prompt, **kwargs)
        except Exception:
            logger.warning("Claude failed, falling back to DeepSeek")
            return await self._call_deepseek(messages, system_prompt, **kwargs)
```

### P1-5: 缺少 API 限流

**位置**: 全局

**问题**: 没有任何限流机制。恶意用户可以无限调用 /chat 接口，导致 API 成本失控。

**建议**: 使用 Redis 实现滑动窗口限流
```python
# 免费用户：10 次/日；付费用户：无限
RATE_LIMIT_FREE = 10
RATE_LIMIT_WINDOW = 86400  # 24 小时

async def check_rate_limit(user_id: str, is_premium: bool, redis: Redis):
    if is_premium:
        return  # 付费用户不限
    key = f"rate_limit:chat:{user_id}:{date.today()}"
    count = await redis.incr(key)
    if count == 1:
        await redis.expire(key, RATE_LIMIT_WINDOW)
    if count > RATE_LIMIT_FREE:
        raise HTTPException(status_code=429, detail="今日对话次数已用完，升级会员可无限对话")
```

### P1-7: 健康数据表缺少加密和合规字段

**位置**: 第四章 4.1，health_data 表

**问题**:
1. 健康数据属于敏感个人信息（PIPL），需要加密存储
2. 缺少 `data_source` 字段（数据来源：HealthKit/Health Connect/手动输入）
3. 缺少 `consent_version` 字段（用户授权时的隐私政策版本）

**建议修改**:
```sql
CREATE TABLE health_data (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    date DATE NOT NULL,

    -- 运动数据（加密存储）
    steps_encrypted BYTEA,           -- AES-256 加密
    distance_km_encrypted BYTEA,
    calories_burned_encrypted BYTEA,
    active_minutes_encrypted BYTEA,

    -- 生理数据（加密存储）
    heart_rate_avg_encrypted BYTEA,
    heart_rate_resting_encrypted BYTEA,
    sleep_hours_encrypted BYTEA,

    -- 元数据（不加密）
    data_source VARCHAR(20) NOT NULL DEFAULT 'health_kit',  -- 数据来源
    consent_version VARCHAR(20),  -- 授权时的隐私政策版本

    created_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
    deleted_at TIMESTAMP,  -- 软删除（PIPL 要求支持数据删除）

    UNIQUE(user_id, date)
);
```

> 实际实现中，可以对整个 JSON 数据加密后存储为 BYTEA，而非逐字段加密（性能更好）。

### P1-10: 生产环境架构过度设计

**位置**: 第六章 6.2

**问题**: MVP 阶段就规划了 PostgreSQL 主从、Redis 哨兵、Celery 异步任务、Prometheus + Grafana 监控。这对个人开发者 MVP 来说太重了。

**建议 MVP 阶段简化为**:
```
单台云服务器（2C4G）:
├── Docker
│   ├── FastAPI (Uvicorn, 2 workers)
│   ├── PostgreSQL (单实例)
│   └── Redis (单实例)
├── Nginx (反向代理 + HTTPS)
└── 日志：直接写文件 + logrotate

用户量 > 500 后再考虑:
├── 数据库读写分离
├── Celery 异步任务
└── 监控系统
```

final router = GoRouter(

    }
    return null;
  },
);

## 八、结论

技术架构的**方向是对的**——Flutter + FastAPI + PostgreSQL + Claude API 是一个合理的技术栈组合，Clean Architecture 分层也正确。问题在于**细节实现**：

1. **4 个 P0 问题**必须修复——SQL 语法错误、Depends() 用法错误、异常泄露、缺少流式输出。这些问题会导致代码直接跑不起来或体验极差。
2. **安全与合规设计完全缺失**——作为一款处理健康数据的 App，这是不可接受的。必须在开发前补充。
3. **LLM 对话核心链路需要补全**——流式输出、token 控制、多模型降级、重试机制，这些是对话产品的核心能力。
4. **开发路线图需要与修订版可行性分析对齐**——从 9 周调整为 7-9 个月。

建议在修复 P0 问题并补充安全/合规设计后，再启动编码工作。
