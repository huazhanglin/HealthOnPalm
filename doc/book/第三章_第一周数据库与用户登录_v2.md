# 第三章 第一周：数据库与用户登录

上一章结束时，你的工位上坐着三个 AI 员工，账号注册完毕，手里有一份 W1 计划。这一章，我们正式开工：把数据库建起来，让用户能注册登录。

这一周结束时，我拿到的东西是：**7 张数据库表、一整套安全策略、一个能注册、登录、填档案、进首页的 App 骨架。** 看起来不起眼，但它是后面所有功能的容器——没有这些表，第二周的 AI 晨报、第三周的健康数据都没有地方放。

本章会大量出现 SQL 代码。**先说清楚：一行都不需要你写，也不需要你看懂每一行。** 你要做的是三件事：让龙虾告诉你今天建什么表、把任务描述交给科泽（Cursor）让它生成 SQL、把 SQL 粘贴到 Supabase 的 SQL Editor 里执行并验收。代码在这本书里的角色，是"施工结果"——你验收它的行为，不是背诵它的语法。

## 3.1 W1 节奏：一天一类事

龙虾给我的 W1 计划拆成了 8 个任务，合计 25 小时，按一周排开。节奏很简单：**一天只干一类事。**

| 任务 | 内容 | 时长 |
|---|---|---|
| T1 | Supabase 项目初始化 + 数据库 Schema（7 张表） | 3h |
| T2 | RLS 安全策略配置 | 2h |
| T3 | 登录认证（Auth） | 3h |
| T4 | uni-app 项目初始化 | 2h |

顺序有讲究：先数据库、再安全策略、再登录、再页面。**容器先于内容**——先把"数据放哪、谁能看"定下来，再写界面。传统团队也是这么排的，只不过他们的顺序靠架构师拍板，我的顺序靠龙虾——而我负责在验收时确认它排得有道理。

下面按实际执行顺序讲。

## 3.2 第一天：7 张表的诞生

### 先想清楚：为什么是这 7 张表

动手建表之前，龙虾先带着我把表的结构过了一遍。这一步千万别跳过——表结构就是 App 的骨架，改界面容易，改表结构伤筋动骨。

HOP 的 7 张表，按用途分三层：

**核心一张：`users`（用户档案表）。** 存每个用户的健康档案：年龄、性别、身高体重、职业、睡眠目标（默认 7.5 小时）、运动水平、偏好训练时段、单次训练时长偏好。它和 Supabase 自动管理的登录账号表（`auth.users`）是一对一关联——登录凭证 Supabase 管，业务档案我们自己的表管，各司其职。这套两层结构怎么运转，3.5 节细讲。

**业务五张：**

- `daily_summaries`（每日摘要）——每个用户每天一条：当天步数、活动热量、站立时长，以及 AI 产出的晨报、训练计划、恢复分（0-100）、训练建议（train / light / rest 三档）。这是整个 App 最核心的一张表。
- `health_memories`（健康记忆）——AI 的长期记忆，向量存储，后面做个性化建议全靠它。表里专门留了记忆类型字段（工作记忆/情景记忆/语义记忆/程序记忆）和重要度打分。
- `conversations`（对话记录）——用户和 AI 的聊天历史。
- `workout_logs`（运动记录）——每次训练的类型、时长、消耗，还有两个很妙的字段：主观疲劳度（1-10 分）和练后心情（五档），这两个是 AI 判断"这个用户练多了还是练少了"的关键依据。
- `sleep_logs`（睡眠记录）——入睡、时长、睡眠阶段。

**监控一张：`token_usage_logs`（用量日志）。** 每次调用大模型花了多少 token、多少钱，全记下来。单独一张表做成本监控——个人开发者没有财务部门，这张表就是我的财务部门。

如果你做的不是健康 App，套这个三层结构就行：一张用户档案表、若干张业务数据表、一张成本监控表。**思考题：做一个记账 App，你会建哪几张表？** 带着这个问题往下读。

### 看一眼代码：普通人在验收什么

以下是 `users` 表的建表 SQL，由科泽（Cursor）生成，我原样贴进 SQL Editor 执行的。我用它告诉你"看不懂语法也能验收"是什么意思：

```sql
CREATE TABLE IF NOT EXISTS public.users (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now(),
  deleted_at TIMESTAMPTZ,

  nickname TEXT,
  avatar_url TEXT,

  age INTEGER,
  gender TEXT CHECK (gender IN ('male', 'female', 'other')),
  height_cm NUMERIC(5,2),
  weight_kg NUMERIC(5,2),
  sleep_goal_hours NUMERIC(3,1) DEFAULT 7.5,

  fitness_level TEXT CHECK (fitness_level IN ('beginner', 'intermediate', 'advanced')),
  preferred_workout_time TEXT CHECK (preferred_workout_time IN ('morning', 'noon', 'evening', 'flexible')),

  onboarding_completed BOOLEAN DEFAULT FALSE,
  last_active_at TIMESTAMPTZ DEFAULT now()
);
```

我验收时看的是这几个"人话"问题：

- **表里有没有我业务要的东西？** 年龄、身高、训练偏好——档案页要填的每一项，表里都有对应字段。这是最重要的验收：**拿着你的产品设想逐项对照**。
- **值域能不能乱填？** `CHECK (gender IN ...)` 这种约束，作用是数据库自己拒绝非法值——运动水平只能三选一，谁也别想填"宗师"。这是在替我省掉一堆校验代码。
- **删用户时数据怎么办？** `ON DELETE CASCADE` 的意思是：删除登录账号时，这个人的所有业务数据跟着删。对内测产品这是干净的做法。另外每张表都有 `deleted_at` 字段——不真删，只标记，行话叫"软删除"，给后悔留余地。

表建完，还要配两样"售后件"：一个 `update_updated_at` 触发器（任何记录被修改时自动刷新更新时间，不用代码操心）和索引（让"查某个用户某天的数据"这类高频查询快起来）。这些也全是科泽生成的，我验收的方式是执行完看有没有报错、到 Table Editor 里肉眼看一眼。

### 三要素提示词：怎么让 AI 建出你要的表

书里说过的提示词三要素——**先读规则、说清上下文和约束、明确要什么**——建表这一步的完整用法是这样的：

```
【规则】严格使用 PostgreSQL 语法，Supabase 环境。
所有表包含 id (UUID)、created_at、updated_at、deleted_at 基础字段。
用户业务数据表通过外键关联 public.users，ON DELETE CASCADE。

【上下文】我在做一个 iOS 健康 App（Health On Palm），用户注册后填写健康档案。
数据库已经有 public.users 表，结构如下：（贴上 users 表 SQL）。
现在需要一张 daily_summaries 表存每日摘要：每个用户每天一条，
包含当天步数/活动热量/站立时长，以及 AI 生成的晨报文本、训练计划、
恢复分（0-100 的数字）和训练建议（只有 train/light/rest 三种取值）。

【要什么】请生成 daily_summaries 的建表 SQL，要求：
1. 每个用户每天只能有一条记录（加唯一约束）；
2. 恢复分超出 0-100、训练建议填了别的值时要直接报错（CHECK 约束）；
3. 附带 (user_id, date) 的索引；
4. 生成后用注释解释每个约束的作用。
```

注意最后一条：**让 AI 自己解释它写的约束**。这是普通人验收代码最好用的招——AI 生成的东西，让 AI 用人话再讲一遍，讲不清的地方往往就是问题所在。

7 张表按"3 个核心表 + 4 个辅助表"分两批执行，第一天收工。验收标准简单粗暴：Table Editor 里 7 张表都在、索引都在、无报错。

## 3.3 第二天：RLS——数据库层面的"各人自扫门前雪"

表建好了，第二天解决一个要命的问题：**怎么保证用户 A 看不到用户 B 的数据？**

健康数据是隐私。如果这个保证只靠前端代码——页面只请求自己的数据——那只要有人绕过 App 直接调用接口，所有人的数据都裸奔。正确做法是**把规则写进数据库本身**：Supabase 的 RLS（Row Level Security，行级安全策略）。

原理一句话：每条数据都问一句"当前登录的人是谁？这行数据的 owner 是不是他？"不是，直接拒绝——不管请求来自哪个页面、哪段代码。

落到代码，是给每张表写几条策略：

```sql
-- 启用 RLS
ALTER TABLE public.users ENABLE ROW LEVEL SECURITY;

-- 用户只能看/改自己的档案
CREATE POLICY "Users can view own profile" ON public.users
  FOR SELECT USING (id = auth.uid());

CREATE POLICY "Users can update own profile" ON public.users
  FOR UPDATE USING (id = auth.uid());

-- 业务表模式一致：user_id 必须等于当前登录者
CREATE POLICY "Users can view own summaries" ON public.daily_summaries
  FOR SELECT USING (user_id = auth.uid());

CREATE POLICY "Users can insert own summaries" ON public.daily_summaries
  FOR INSERT WITH CHECK (user_id = auth.uid());
```

细心的读者会发现 `users` 表除了查和改，还有一条 INSERT 策略（`WITH CHECK (id = auth.uid())`）——它不是摆设，是给客户端"补建档案"兜底用的，3.5 节会讲清楚它和触发器的分工。

七张表、每张表若干条策略，模式高度一致，科泽（Cursor）一次生成。真正值得花时间的是**验证它真的生效**——不能因为"AI 说配好了"就信。我的验证分两层：

**第一层，SQL 里模拟攻击：**

```sql
-- 未登录用户查 users 表：应该什么都查不到
SET ROLE anon;
SELECT * FROM public.users;

-- 模拟某个登录用户：只能查到自己那一行
SET ROLE authenticated;
SET request.jwt.claims.sub = 'test-user-id';
SELECT * FROM public.users WHERE id = 'test-user-id';
```

**第二层，Dashboard 里人工核对。** 打开 Authentication → Policies，把 7 张表的策略逐张过一遍，确认每张业务表都有"只能看自己的"策略、没有漏网之鱼。

这一步的验收标准只有一句话：**在未登录状态下查任何业务表，都必须返回空。** 做不到就打回重改。安全这件事，没有"大概齐"。

顺带一提：每张表都重复出现的 `user_id = auth.uid()` 让我起过"能不能简化"的念头。答案是不能也不必——RLS 策略天生就该每表显式声明，宁可重复，不可遗漏。这是数据库安全和普通代码品味不一样的地方。

## 3.4 第三天：登录——以及第一个被推翻的计划

数据库和安全性就位，第三天做登录。这里有个值得完整讲述的故事，因为它演示了"计划被推翻"的全过程。

**W1 计划里的登录方案是：手机号 + 验证码。** 流程你也熟：输手机号、收短信、填验证码。科泽（Cursor）生成的登录页调 `signInWithOtp()` 发验证码、`verifyOtp()` 验证，Supabase 还贴心地提供了一组测试号码（+1 555 555 1234 之类，验证码固定 123456），开发阶段不花一分钱短信费。当时走得挺顺，测试号码登录成功、跳转首页、状态保持，验收全过。

**但这个方案在第三周被推翻了。** 原因很实际：

- 正式发短信要走短信通道，要么花钱接第三方服务，要么被审核流程卡住；
- 内测阶段就十几个种子用户，为十几个人搭一条短信链路，成本收益完全不匹配；
- 种子用户是我一个个拉进来的熟人，邮箱注册没有任何门槛。

所以 W3 中期，登录改成了**邮箱 + 密码**：Supabase 的 Email Provider 开箱即用，零额外成本，开户只要三十秒。代价是原来用手机号登录的会话全部作废，老用户（其实也就我自己）用邮箱重新注册了一遍。

这段经历想教给你两件事：

**第一，登录方案不是技术问题，是成本问题。** 手机验证码体验好，但为它付出的通道成本和依赖，对内测期的产品是纯负担。做选择时问自己：我这个阶段有多少用户？为他们的登录体验付这笔钱，值吗？等产品验证成功、用户量上来了，再切回手机号登录也不迟——登录方式是可以换的，数据库结构才是难改的。

**第二，内测期记得关闭"邮箱确认"。** Supabase 默认注册后发确认邮件，点链接才激活。内测阶段用户就是你自己拉的人，这层确认纯属摩擦。在 Authentication 设置里把 Confirm email 关掉，注册即用。等开放注册时再打开，防机器人。

顺便说一句前端代码在这里的角色：注册按钮背后只有一个动作——调用 Supabase 的 `signUp`（或 `signUpWithEmail`）。**前端不碰 `public.users`**，注册瞬间自动建档这件事，由数据库侧的触发器完成。这是接下来 3.5 节的主角。

登录页的提示词，三要素版本：

```
【规则】Vue 3 + TypeScript + uni-app，使用 @supabase/supabase-js v2。
所有 Supabase 调用集中在 api/supabase-auth.ts，页面不直接引 SDK。
【上下文】App 处于内测阶段，登录方式为邮箱+密码（注册/登录同一个表单，
未注册邮箱提交注册逻辑，已注册走登录逻辑）。
Supabase 的 Confirm email 已关闭，注册成功即视为登录。
注册建档由数据库触发器自动完成，前端只调 signUp，不写 public.users。
【要什么】生成登录页 pages/login/index.vue：
1. 邮箱、密码输入，登录/注册按钮，错误提示用 Toast；
2. 登录成功后把用户状态存进 Pinia（stores/user.ts），跳转新手引导页；
3. 登录失败要区分"密码错误"和"邮箱未注册"，给出不同的提示文案；
4. 附一段注释，解释 session 是怎么在刷新后保持的。
```

## 3.5 第四、五天：从登录记录到有血有肉的用户

登录打通后，剩下的是把"用户"从一行登录记录变成一个有档案的人。这一节是本周最有"数据库味"的部分，我把它拆成三件事讲：注册瞬间发生了什么、引导流程长什么样、以及"断点"到底断在哪。

### 两张表和一个触发器：注册瞬间的自动建档

先看清楚账号的两层结构——**这是本节最重要的一张图，也是很多人做 Supabase 会搞混的地方**：

| 层 | 作用 |
|---|---|
| `auth.users` | 登录凭证。Supabase Auth 在 signUp 时自动创建，**App 代码不直接插这张表** |
| `public.users` | 业务档案。id 等于 auth.users.id，外键 `REFERENCES auth.users(id) ON DELETE CASCADE` |
| 触发器 | 注册瞬间给业务表自动插一行空档案——主路径 |
| RLS INSERT 策略 | 给客户端"补档"用的兜底（触发器没生效时的 upsert），**不是建档的主路径** |

自动建档靠的是下面这个触发器——这段 SQL 是 W1 T2 任务在 Dashboard 的 SQL Editor 里执行的（一个真实的插曲：它没有进代码仓库的 `supabase/migrations/` 目录，所以后来翻代码是找不到它的，得回 Dashboard 核对。这个教训后面小版本踩过，你先记住"触发器可能只活在数据库里"就行）：

```sql
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO public.users (id, nickname, avatar_url, created_at, last_active_at)
  VALUES (
    NEW.id,
    COALESCE(NEW.raw_user_meta_data->>'nickname', NEW.phone),
    NEW.raw_user_meta_data->>'avatar_url',
    NOW(),
    NOW()
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW
  EXECUTE FUNCTION public.handle_new_user();
```

用人话拆解这段代码的四个要点：

- **时机**：`AFTER INSERT ON auth.users`——每注册一个账号，触发器跑一次。Auth 表进新人，业务表立刻跟上，不需要前端多写一行代码。
- **`SECURITY DEFINER`**：函数以所有者权限运行，**绕过 RLS**。道理很简单：注册瞬间用户可能还没有有效的登录态，如果让 RLS 管着，"替新用户插自己的档案"这个动作会被自己的安全策略拦住。建档不走用户 JWT，是设计好的，不是漏洞。
- **只写四个业务字段**（id、昵称、头像、时间戳）。注意 `onboarding_completed` 没写——它靠建表时的 `DEFAULT FALSE` 默认值。也就是说：**每个新用户注册完，档案里都写着"引导未完成"，新人必走新手引导，一个都跑不掉。**
- **昵称的 COALESCE**：优先取注册时带的 nickname，其次手机号。但现行方案是邮箱注册——一般不传 nickname，也没有 phone，所以这行的昵称通常是 NULL，等引导结束时用邮箱前缀补上。

触发器装没装好，用一句话核验（Dashboard → SQL Editor）：

```sql
SELECT tgname, pg_get_triggerdef(oid)
FROM pg_trigger
WHERE tgname = 'on_auth_user_created';
```

查得到定义就说明在岗；查不到，新注册的用户在 `public.users` 里就是"黑户"——这正是 RLS INSERT 策略存在的意义：**兜底**。前端在引导完成时（`completeOnboarding` / 更新档案）的逻辑是：先 `UPDATE` 自己那行；如果发现没有行（触发器没装、执行失败、历史遗留账号），就 `upsert` 一条——代码注释里写得明白："兼容触发器未生效的情况"。主路径是触发器，客户端补档是保险丝，RLS INSERT 策略只负责约束"你只能插自己的 id"，两边互不越界。

### 新手引导：五步，克制地收五个字段

引导页（`uni-app/src/pages/onboarding/index.vue`）一共五步：**欢迎 → 健康档案 → 运动偏好 → 数据授权 → 完成。**

先说设计上的克制：引导里只收**年龄、身高、体重、运动水平、偏好训练时间**这五个字段。性别、职业、睡眠目标、训练时长这些统统不问——它们躺在"我的"档案页里，用户有空再补。道理很简单：**注册后的每一步都在流失用户，引导只问"不问就没法开工"的问题。**

逐步看：

**第 1 步 · 欢迎。** 标题"欢迎使用 Health On Palm"，说明"每天根据你的身体状态，自动规划下一步行动"，一个"开始"按钮。无任何校验。

**第 2 步 · 健康档案（必填，过不了不能下一步）。** 年龄选择器 18–80；身高 100–250 cm；体重 30–200 kg。填错弹 Toast："请选择年龄""请填写有效身高"——每条失败提示对应一条校验规则。可以点"‹ 上一步"回去改。

**第 3 步 · 运动偏好（必填）。** 运动水平三选一：初级/中级/高级（对应库里 beginner/intermediate/advanced）；偏好训练时间四选一：早晨/中午/晚上/灵活。

**第 4 步 · 健康数据授权（本页不弹系统授权）。** 说明会读步数、睡眠、训练，然后"继续"和"稍后授权"两个按钮——**点了都不会真的弹 HealthKit 授权框**，都只是进入下一步。真正的授权发生在引导结束之后：路由函数发现是 iOS 且还没授权，才带去 `/pages/healthkit/authorize?from=first` 页面，否则直接进首页。这是个很细但很对的体验设计：授权弹窗出现在用户理解了"为什么要授权"之后，而不是流程中间猝不及防地打断。

**第 5 步 · 完成。** 进入这一步，代码里有个 `watch(currentStep)`，发现到终点就自动调用一次 `finishOnboarding()`（只触发一次），页面上同时保留"进入首页"按钮（保存中显示"保存中..."）。

提交的载荷（`buildOnboardingPayload`）里有个值得单独讲的小设计——**昵称的自动生成**，三级 fallback：邮箱 @ 前缀取最长 20 字；不行就旧手机号末四位拼"用户xxxx"；再不行就叫"健康用户"。用户不用填昵称，但进首页时永远不会看到一片空白。

落库动作就是前面说的兜底逻辑：先 `UPDATE public.users`，没行再 `upsert`；成功后更新本地用户状态、写入本地标记、Toast"准备就绪"，约 500ms 后路由离开。

### "断点续填"的真相：断在哪，续在哪

这一小节纠正一个我自己都差点写错的认知。

我最初以为引导做了"断点续填"——填到第 2 步杀掉 App，下次从第 3 步接着填。**实际上没有，也不需要。** 中间步骤的表单只活在页面内存里，杀掉 App 再打开，引导从第 1 步重新来。五个字段，重填一遍不到一分钟，为此做云端草稿纯属过度设计。

真正的"断点"只有一道：**整段引导，完成，还是没完成。** 它由三道机制守着：

1. **权威字段**：`public.users.onboarding_completed`。登录后路由函数查它——false 或没有档案，进引导页；true，走 HealthKit 门或直接首页。
2. **本地缓存**：`health-agent-onboarding-done`，按 userId 记录完成状态。作用是少打一次接口、以及拉档案失败时不把已完成的老用户打回欢迎页。
3. **门禁**：首页、助手、训练、记录、档案这些主页面，每次 `onShow` 都调 `ensureOnboarded()` 检查，没完成就强制跳回引导页；反过来，已完成用户万一误入引导页，`onShow` 发现 `onboarding_completed` 是 true，直接 `reLaunch` 回首页。

所以正确的说法是：**步骤内没有草稿，断点是"是否完成过引导"——没完成，每次从欢迎页开始；完成了，登录和所有主页面都不会再放你进向导。**

把注册到首页的完整链路串起来，是这样一条时序（你可以拿这张图对照自己的实现检查一遍）：

```
signUp(邮箱, 密码)
  → Supabase Auth 写入 auth.users
  → 触发器 on_auth_user_created 触发
  → public.users 插入空档案（onboarding_completed = false）
登录后路由
  → 查 onboarding_completed = false → 进引导页
  → 五步填写（表单只在内存，中途退出则下次从头开始）
  → 第 5 步 completeOnboarding()：UPDATE 置 onboarding_completed = true
    （无行则 upsert 兜底）+ 写本地标记
  → （iOS 且未授权）HealthKit 授权页
  → 首页（各主页 onShow 持续守门）
```

## 常见问题

**Q：我完全不懂 SQL，真的能做数据库设计吗？**
你不懂语法，但你懂业务——而表设计首先是业务问题：你要存什么、什么和什么是一对多、什么字段只能填固定的几个值。这些你用中文跟 AI 说清楚（就像 3.2 节那个提示词），语法它包办。你的验收动作也全是中文的："这个值填错了有没有被拦住？""这行数据删了，关联数据还在不在？"

**Q：为什么要 7 张表？都放一张表里不行吗？**
技术上能，业务上是灾难。想象一个 Excel：一张表存"用户+每天摘要+对话+运动"，每天给每个用户加一行，绝大部分列都是空的，查询和权限控制都没法做。拆表的本质是**一类事实一张表**：用户的档案是一类事实，每天的摘要是一类事实。判据也很好记：会不会有两个"主体"（一个用户、一天）抢同一行？会，就该拆。

**Q：有触发器自动建档，为什么还要 RLS 的 INSERT 策略？两者什么关系？**
好问题，这正是最容易搞混的地方。**触发器是主路径**：注册瞬间由数据库自动插空档案，它以 `SECURITY DEFINER` 权限运行，**不走 RLS**。**RLS INSERT 策略是兜底**：万一触发器没装、执行失败或存在历史账号，前端在引导完成时先 UPDATE、没行再 upsert 补一条——这条策略约束的是这次客户端写入"只能插自己的 id"。一句话：触发器负责"出生时建档"，RLS 策略负责"补档时不出轨"，两者不重复、不冲突。

**Q：RLS 策略那么多条，AI 会不会漏写？**
会漏，所以要验收。我的做法：让 AI 生成完策略后，**再让它输出一张"表 × 操作（查/增/改/删）"的核对表**，声明每格对应哪条策略；对着表逐格检查，缺一格补一格。AI 生成的东西，用 AI 生成的清单来核对，再人工抽查——这个组合拳比肉眼扫 SQL 靠谱得多。

**Q：登录方案我该学 HOP 用邮箱密码吗？**
内测期，是的，理由本章已经讲过。但请记住它是个阶段性选择：用户量上来、或你的产品面向大众（用户没有邮箱使用习惯），就该换手机号或微信登录。Supabase 的 Auth 是可插拔的——登录方式可以后换，前提是你把"登录凭证"和"业务档案"分开存（就像我们 auth.users 和 public.users 那样），换登录方式时业务数据一根毫毛都不用动。

**Q：软删除（deleted_at）和真删除怎么选？**
内测期建议软删除：数据无价，用户误删还能救回来，而且删除动作只是改一个字段，最安全。等产品成熟、合规要求明确（比如用户注销必须彻底删数据），再做"硬删除"的清理流程。`ON DELETE CASCADE` 管的是账号注销时连坐删除，和日常软删除是两回事。

**Q：要不要给引导流程做"填一半保存草稿"？**
不要，除非你的引导有几十项。HOP 引导五个字段、一分钟填完，做云端草稿的成本（多一张表、多一套读写、多一堆边界情况）远超收益。正确的断点粒度是"完成/未完成"整段式的：`onboarding_completed` 一个布尔字段 + 本地缓存，就覆盖了所有场景。**先问"用户重填一遍的成本有多高"，再决定要不要存草稿。**
