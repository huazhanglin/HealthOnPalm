# 我用 AI 造 App（四）：先造假数据——零基础的 AI 功能周

> 系列第四篇。前三篇讲了立项、工具和第一周的数据库与登录（文末有链接），这篇进入很多人最关心的部分：**AI 功能是怎么做出来的**——以及为什么我的第一个决定是"造假数据"。

## 这一周做成了什么

一句话：**跑通 Morning Brief Agent，用户每天早上能收到 AI 健康简报，还能和 AI 聊天。**

拆开是十一个模块：Mock 数据服务、恢复分计算、晨报 Agent、问答 Agent、训练 Agent、安全 Agent、记忆 Agent、对话界面、Edge Functions 部署、定时推送、集成测试。计划估时 43 小时、7 个日历日。

而支撑这一切的健康数据——步数、睡眠、心率——**全是假的**。

## 一、为什么先造假数据

W2 开工前有个选择题：先接 HealthKit 真实数据，还是先造假数据跑通 AI 链路？选了后者，三个理由：

1. **依赖解耦**。HealthKit 授权、字段对齐、单位换算，每一环都可能卡住你。AI 链路和真实数据绑死，任何一环卡壳整条链停摆。
2. **问题隔离**。假数据是已知正确的输入。晨报不对，问题一定在 AI 链路；等换上真数据再出问题，去 HealthKit 那头查。假数据就是调试时被固定死的变量。
3. **价值优先**。产品的核心价值是"AI 给的建议靠不靠谱"，不是"能不能读步数"。AI 说不靠谱的话，接真实数据毫无意义。

Mock 服务是个 Edge Function，生成规则**按人设造**：步数初级 3000–7000 / 中级 5000–11000 / 高级 8000–16000；静息心率同样按运动水平分档；睡眠围绕用户目标 ±1.5h；心情按 0.1/0.35/0.35/0.2 的权重分布。档案联动让 AI 收到的上下文自洽——不会出现"每天走 15000 步的初学者"。代码里写死一行注释：`TODO: W3 替换为真实 HealthKit 数据`。

## 二、OpenRouter 之死：AI 帮不上忙的时刻

设计阶段选的 LLM 入口是 OpenRouter。计划照做、代码照写，到 W2 部署时发现：**国内无法访问。**

这个问题 AI 提前发现不了——它的知识截止日期里 OpenRouter 活得好好的。AI 的答案全在模型参数里，参数里没有"此刻的墙"。

切到 SiliconFlow（硅基流动）：国内直连、OpenAI 兼容。牵连三处：

- 模型路径：`openrouter/deepseek/deepseek-chat-v3` → `siliconflow/deepseek-ai/DeepSeek-V3`
- Embedding：`text-embedding-3-small`（1536 维）→ `BAAI/bge-m3`（1024 维）
- 数据库：W1 建表是 `VECTOR(1536)`，要 ALTER 成 1024 维

第三项最阴险：设计文档、建表 SQL、Edge Function 代码里写的全是 1536，不匹配则所有向量检索运行时报错。整个切换半天。

**教训：开工前用最小代价验证基础设施——一个 curl 请求的事。设计文档验证不了"现在、此地、这个网络"。**

## 三、恢复分：规则算数字，AI 解释数字

晨报要回答"今天练、轻度还是休息"。让 LLM 拍脑袋？它没有稳定标准，今天说练明天说休息，用户很快不信。所以先算一个**确定性的恢复分**（0–100），AI 只负责解释它。

W2 版算法四项加权：

| 组成 | 权重 | 逻辑 |
|---|---|---|
| 睡眠分 | 40 | min(40, 睡眠比例×30 + 质量分/100×10)；比例上限 1.3——多睡不加分 |
| 休息日分 | 30 | 连续休息每日 +10 封顶 30；今天已运动则归 0 |
| 活动量分 | 20 | min(20, 步数比例×13.3)；8000 步为基准，比例上限 1.5 |
| 心情分 | 10 | great 10 / good 7.5 / normal 5 / tired 2.5 |

≥80 train；50–79 light；<50 rest。

实现方式是**先写测试再实现**，四个用例：8h 睡眠 + 8000 步 + 心情不错 → ≥70；3.5h 睡眠 + 疲惫 → ≤35；连休 2 天 + 好睡眠 → train；极度疲劳 → rest。

一个诚实的细节：休息日分设计里写着"今天已运动归 0"，但当周代码里连续休息天数**写死为 0**——注释"MVP 暂不计算"。也就是说 W2 的用户永远拿不到休息日加分。发现了，不修：那个阶段的目标是链路转起来，不是数字完美。精细规则（睡眠中性分、近 7 日休息平衡）W4 才重做。

**规则算数字、AI 解释数字**——这个分工建议所有做 AI 产品的人抄走：LLM 擅长把"74 分、轻度活动"翻译成人话，不擅长当基准线。

## 四、晨报 Agent：链路是长出来的

Morning Brief Agent 是 Supabase Edge Function，W2 当周的主路径：

```
读取用户档案
  → mock-health-data 拿今日数据（TODO: W3 换 HealthKit）
  → recovery-score 算恢复分与建议
  → 组装 Prompt，调 DeepSeek-V3 生成晨报
  → 本地拼接免责声明（MVP 简化版）
  → upsert 写入 daily_summaries（含 context_snapshot 快照）
  → 记 token 消耗到 token_usage_logs
```

注意这是"当周主路径"——完整的 Safety Agent 和记忆层是 W2 中后段才补的，补上后晨报函数才接入正式的 `runSafetyCheck`。对话路径（用户发问）是另一条链：问句先过安全检查、带工作记忆、生成、再过一遍安全检查出去。**功能是一条条长出来的，不是一天齐装满员的。**

system prompt（W2 计划稿原文，后来现行代码把免责声明改由 Safety 层统一处理）：

```
你是 HOP，一位专业、温暖、简洁的个人健康教练。
你的特点：
- 简洁直接，不啰嗦
- 语言像朋友在说，不像医生
- 每天只给一个重点行动建议（不多贪）
- 结尾必须附注"以上为非医疗建议，如有不适请咨询医生"

禁止：
- 不提诊断、治疗、处方、药物推荐
- 不给具体重量/组数/次数建议
- 不制造焦虑
```

user prompt 填入档案 + 数据 + 恢复分，要求输出问候、一个重点建议、理由、一个可执行操作，**最多 150 字**。参数：max_tokens 800，temperature 0.7。

两个工程细节：每次晨报入库带 `context_snapshot`（原始输入快照，事后可回答"那天 AI 为什么这么建议"）；token 消耗全记 `token_usage_logs`——**AI 每说一句话都是钱**。

前端配合一条硬规则：**打开 App 先查今天有没有简报，有读库、没有才生成**——一个用户一天最多一次调用。

回顾定性：约 10 个 Edge Function，约 8 个 AI 生成初稿、人工微调部署。前提是执行计划里接口规范、Schema、Prompt 全部写清。同样是让 AI 写代码，"你不懂、AI 也不懂"时它生成看起来对、跑起来错的代码；"你懂、它执行"时又快又稳。**你在流程里的位置，决定 AI 的产出质量。**

## 五、Safety：便宜的第一层 + 聪明的第二层

健康 AI 绕不开医疗问题。两层审查：

**第一层正则（毫秒级、确定性）**，三个动作：

- **BLOCK**：诊断用语（诊断/确诊/患有/得了）、药品、严重症状、精神危机、病名清单——直接拒答
- **REFER**：持续/严重表述（一直疼/持续疼/流血/骨折）、孕产、儿童老人——引导就医但不硬拒
- **ALLOW**：正常话题

**第二层 LLM 复查**：过了第一层才进，按"是否含诊断/治疗/处方、是否制造焦虑"输出结构化判断；`skip_llm_check` 可关（MVP 省 token）；**LLM 调用失败保守判 unsafe**——宁错杀不放过。

测试用例就是"坏人语录"：BLOCK 组"你可能患有高血压，建议服用降压药""根据你的症状，我诊断你可能有糖尿病"；REFER 组"你最近一直头疼，应该去看医生"；ALLOW 组"有氧 30 分钟""睡前少看手机"。集成清单还有组合拳：**"我可能得了高血压"必须被拦**——同时命中"得了"+"高血压"。

第一层能被绕吗？能——"我的血压有点高"这种软性说法凑不齐字面关键词（这是假设示例，计划用例都是第一层直接拦住的重话），这正是第二层存在的意义：字面匹配交给正则，语义理解交给 LLM。**便宜的第一层挡掉高频，聪明的第二层兜住疑难**——这个分层思路，缓存和风控都一样。

## 六、记忆：草稿纸和大事记

四层记忆体系设计文档里全画了，MVP 只做两层：

**L1 工作记忆**（memory-working）：管今天聊了什么。conversations 表按用户+日期一条；`MAX_MESSAGES = 20`（截断留最近 20 条），`SUMMARY_THRESHOLD = 12`（超 12 轮触发 LLM 摘要存 `context_summary`）。压缩的动机很直白：每轮原文都传给模型，token 成本爆炸；一段摘要几十 token。**记忆压缩的本质是省钱。**

**L2 情景记忆**（memory-episodic）：管发生过什么。训练完成、坚持百天这类事件经 bge-m3 转向量存 `health_memories`，靠语义相似度检索（match_health_memories RPC）——"我之前练肩的时候什么感觉"也能召回。这就是向量列从 1536 ALTER 到 1024 的用途。

一个管今天，一个管一生。草稿纸每天换，大事记越攒越厚。

## 七、被砍掉的定时推送，和"一周变两周"的账

计划里有每天 7:30 定时推送，没做。原因：推送要走订阅授权，用户不点就推不了，为不确定的功能搭链路不值；且 HOP 的场景是"打开时看最新状态"——打开时生成反而拿到此刻的真实数据（比如今天已运动，简报跟着变）。最终形态：**有就读库、没有现生成。**

最后算账——这里有个很多人会写错的账。

**计划：7 个日历日、估时 43h。回顾：记成两周。净投入：约 17h。**

日历拉长、工时只有四成，这不是赶工失败。摊开看：43h 里有整项被砍的推送；日历变长有三条可查的原因——OpenRouter 切换是计划外的半天；W3 的 HealthKit 插件调研 7 月 29 日就交了（W2 的 Day 9），两线日历叠着走但分账记；W1 计划写到 7 月 30 日，W2 从 7 月 28 日起算，两个"周"本就不互斥。

OPC（一个人+AI）的真实形状：**晚上做一点、被基础设施打断、和下一阶段交叉。** 看到独立开发者晒"两周做完"，先问日历里的净投入——多半比你想的少，也比他自己晒的少。
