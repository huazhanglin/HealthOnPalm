# 我用 AI 造 App（六）：第四周——AI 出计划，但只能从我圈好的菜里点

> 系列第六篇。前五篇讲了立项、AI 分工、数据库、假数据、自研 HealthKit 插件和真数据（文末有链接）。这篇进入第四周：没有开新大陆，而是对前三周所有功能做一次**总清算**——训练闭环、恢复分重写、赶走"昨天"的幽灵。

## 这一周做成了什么

一句话：**训练闭环第一次真正转起来 + 恢复分三桩冤案平反 + 缓存与自动同步到位。** 版本约 0.3.8。

W4 没有新点子，驱动它的是一张问题清单——来自开发者自测和种子用户的只言片语：

- 三个 Tab，训练计划和 AI 助手藏在二级页里，找不到
- Workout Agent 只会说"建议适度训练"——没有动作清单，没有打卡，建议完就完了
- 恢复分的心情维度写死 normal，App 根本不问用户累不累
- 没有真实睡眠时，恢复分要么打 0，要么被 Mock 时长糊弄
- "练 7 休 2"的人，训练日休息维直接 0 分——越自律，分越低
- Tab 切回首页就全量刷新，慢
- **早上打开 App，显示的还是昨天的数据**
- 基础代谢字段一直空着、说明书还是三 Tab 的老黄历

任务表 T1–T11 全部从这张清单翻译而来。日历上，执行记录从 8 月 12 日写到 8 月 23 日——跨了十二天；开发回顾里这一周记作 1.5 周。两套都算数：**个人开发者的"周"是记账单位，不是物理单位。**

## 一、动作库：LLM 只能选 ID，禁止编造

W4 最大的一块工程。数据来源是 **wger**——一个开源健身数据项目（CC BY-SA 许可）：全量约 **860 条**已审核动作进自建表，其中约 **160 条**标记 featured，专供 AI 出计划。

核心产品规则一条：

**LLM 只能从候选清单里选动作 ID，禁止编造。** 而且围栏比想象中窄——Agent 调用时传 `featuredOnly: true`，**AI 只能在 160 条精选里点菜，不是在 860 条里自由发挥。**

加上强度闸门：恢复分 < 50 **或建议为 rest** 时只许出 light/热身/拉伸；50–80 出 light/moderate 为主；> 80 正常强度。计划结构固定：热身 1–2 + 正式 3–5 + 拉伸 1–2，生成后缓存进当日 `daily_summaries.ai_plan`。

一个刻意克制的点：**计划不给重量、组数、次数。** 不是做不到，是不该做——非医疗的健康 App 把"练多重"写死给用户，出了事说不清。

打卡闭环：训练页看计划摘要和动作详情（含 wger 署名，开源协议要求的）→ 点"完成并打卡" → `workout_logs` 写入 `source = 'ai_suggested'` 的记录，回写 `exercise_ids`。更正一个容易想当然的印象：**exercise_ids 不是老早预留的，就是这次随动作库一起加的**（`20260819_exercise_catalog.sql`）——建库、加列、回写，同一刀落成。

## 二、五 Tab，和一个自找的坑

导航变成「**首页 / 助手 / 训练 / 记录 / 我的**」，同时删掉两个重复入口——Tab 里有的，别处不再摆第二份。

但改动顺手挖出一个坑：新 TabBar 组件的切换用了 `uni.redirectTo`——**销毁当前页、打开新页**。每次回首页，页面重建、内存清零、全量刷新重来。用户就一个感觉：慢。

这个坑当周填了一半（缓存，见第四节），另一半（原生 tabBar + switchTab）排进 W5。教训一句话：**redirectTo 适合"走完就别回头"的流程页（登录、引导），不适合当主框架用。**

顺带一个不起眼的 P1：手动记录的运动类型扩到**约 19 种**，和计划页共用同一份 `workout.ts` 定义——手记的羽毛球和 AI 计划里的羽毛球，在任何统计里是同一种东西。**字典只有一份，是所有数据合并的前提。**

## 三、恢复分重写：三桩冤案

恢复分四维比例没动（睡眠 40 + 休息 30 + 活动 20 + 心情 10），W4 修的是三个冤案。

**冤案一：没睡眠数据的人。** 旧规则下要么拿 Mock 顶包，要么打 0。新规则：给**中性分 32/40**，打上 `sleep_missing = true`，首页直说"睡眠数据缺失，恢复分仅供参考"。**不知道，就承认不知道——别假装知道，也别惩罚不知道的人。**

**冤案二："练 7 休 2"的人。** 旧规则看"今天休息了没有"，训练日休息维 0 分。新规则取两条路较高者：连续无训练天数 × 10 封顶 30；近 7 天休息天数映射——**休息 1 天得 22，≥2 天得 30**。指标的时间窗从"今天有没有练"变成"最近有没有安排休息"——时间窗变了，冤案就翻案了。

**冤案三：心情被代表的人。** 旧规则心情写死 normal——按 W2 公式（great 10 / good 7.5 / normal 5 / tired 2.5），**所有人每天都拿同一个 5 分**。新规则：新增 `mood_logs` 表，四档重新定值——很好 10 / 不错 9 / 一般 8 / 疲惫 4——没记录时仍回退 normal（新档位下 8 分），不逼打卡。

工程上值得抄的一笔：恢复分逻辑抽成 `supabase/functions/_shared/recovery.ts`，recovery-score 和 morning-brief 两个函数**共用同一份代码**。**同一件事的计算逻辑，物理上只允许存在一份。**

## 四、缓存与自动同步：赶走"昨天"的幽灵

「早上打开 App，还是昨天的简报」——幽灵的成因有两个：首页只读云端、从不主动拉手机数据；App 跨日保活时，内存里的"今天"还是昨天。

**缓存**：一个 Pinia store 按"用户 + 本地日期"存首页快照。5 分钟内秒开不请求；过期先给旧数据、静默刷新在背后跑；记录运动/睡眠/心情或同步后立刻失效；**跨日或换用户直接丢弃**——幽灵的巢穴，一发现就拆。

**自动同步规则表**：

| 场景 | 行为 |
|---|---|
| 进入首页/授权页 | 距上次同步 ≥ 30 分钟或已跨日 → 自动拉 HealthKit |
| 生成/刷新晨报 | 先强制同步（60 秒内刚同步过则跳过） |
| 手动点刷新 | 立即同步 |
| 跨日 | 丢弃昨日缓存，再同步 |

顺手修了一个时区 bug：sync-healthkit 缺 date 时原来按 UTC 算"今天"——**东八区凌晨一点，UTC 还是前一天**，凌晨的记录会被写进"昨天"。改成 Asia/Shanghai。**服务器没有时区概念，你的用户有。**

## 五、数据补齐与一条"不读"的边界

W3 插件清单里写了基础代谢但没真查——W4 补上，连着一批新类型：距离、爬楼、最高/步行心率、**HRV、血氧、呼吸频率、VO₂ Max**。口径备注：对照表 15 行，代码 16 个 identifier（静息/平均心率拆成两项）。

两个值得停一下的设计：

**版本号驱动的重授权。** 读取类型扩了，但用户 W3 只批过旧清单。代码里放 `HEALTHKIT_READ_TYPES_VERSION = 2`：版本落后的用户同步前再走一遍授权，**系统只弹新增类型**。任何读系统权限的 App 都用得上。

**故意不读的清单。** 病历、化验、用药、经期、饮食日记——HealthKit 里都有，HOP **一个都不读**。只读"活动/睡眠/心肺恢复"，临床数据一律不碰。**一个健康 App 的隐私边界，最好写在"它拒绝读什么"上。**

工程红线三条：改了 Swift **必须重打自定义基座**；`20260821` migration 给 daily_summaries 加 7 个新列；权限清单变了，隐私文案（`NSHealthShareUsageDescription`）必须跟着变——审核看的就是这个。

## 六、证书踩坑：一次领了任务编号的坑

W4-T11，P2 优先级，任务内容就一行字："记录一次踩坑"——踩坑本身被排进了任务表。

现象：HBuilderX 重打自定义基座后真机安装失败。排除掉"删 TestFlight 包"和版本号（0.3.8 / 138）两个嫌疑后找到根因：云打包时**选成了 TestFlight 用的发布证书**。规则表一张：

| 场景 | 证书 |
|---|---|
| USB 自定义调试基座 | Development 证书 + Development profile（含本机 UDID） |
| TestFlight / 上架 | Distribution 证书 + App Store profile（不需 UDID） |

改回开发证书，恢复。日期 2026-08-21。**踩过的坑不是聊天记录，是有编号、有表格、有修复记录的资产。**

## 七、没做的清单

W4 的另一半成绩是**没做的**：Sleep Insight Agent（先保证睡眠数据稳定进来再谈洞察）、Weekly Review（日闭环没转完，周报是空中楼阁）、支付（还在免费内测）、**公开测试扩面——理由一行字：先修同步、导航、说明书**。

顺延不等于丢弃：原生 tabBar、两个 Agent、血压等生活方式指标、扩面、上架材料，全部进了 W5 候选清单。**砍掉的任务也要有清单，它记录的是"什么时候、为什么"放下。**

## 八、验收与账本

**P0 九项全过**——第九项最不起眼也最重要：**相关 SQL 已在目标项目执行**。migration 没跑，前面八项都是空中楼阁。P1 两项（说明书 v1.1、运动类型扩容）也全过。这是四周以来最干净的一次验收。

账本要把"缺"和"有"说精确：执行记录里没有逐任务分项；**整周数字以开发回顾合计为准——净投入约 25 小时、AI 参与度约 72%**（多数任务标"高"，缓存/自动同步标"中"）、日历 1.5 周。缺的是"每个函数几小时"那种明细。硬编一条"动作库 4 小时"式的假明细，比空着更有害。

四周曲线：**8h → 17h → 21h → 25h**，逐周走高；AI 参与度持平。全项目到 W4 为止：**6.5 周、约 71 小时、AI 平均约 73%。**

---

第四周结束（按日历说，是第十二天结束），HOP 第一次拥有一个完整转动的闭环：**数据进来，分数算出，计划生成，打卡回写，明天的分数因此不同。** AI 在环里干的活，从"说漂亮话"变成"围着围栏做排列组合"；人干的活，从"审代码"变成"定边界"——哪些数据不读、哪些重量不给、哪些 Agent 先不做。

但环转起来之后，最大的问题变了：**它只在开发者自己的手机上转。** 扩面还没发生，反馈追踪表至今仍是空模板——下一周要还的债不是代码，是"发出去"这个动作。
