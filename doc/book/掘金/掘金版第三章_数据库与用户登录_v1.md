# 我用 AI 造 App（三）：7 张表、RLS 双保险和登录——零基础的第一周

> 系列第三篇。前两篇讲了项目立项和工具准备（见文末），这篇进入正式开发：第一周（W1），我们把数据库建好，让用户能注册登录。我依然一行代码不会写——所有 SQL 都是 AI 生成的，我的工作是让它建出我想要的表，并验证它没骗我。

## 这一周做成了什么

一句话：**7 张数据库表、一整套安全策略、一个能注册、登录、填档案、进首页的 App 骨架。**

看起来不起眼，但它是后面所有功能的容器。没有这些表，第二周的 AI 晨报、第三周的健康数据都没有地方放。

W1 计划拆成 8 个任务，合计 25 小时：

| 任务 | 内容 | 时长 |
|---|---|---|
| T1 | Supabase 项目初始化 + Schema（7 张表） | 3h |
| T2 | RLS 安全策略配置 | 2h |
| T3 | 登录认证 | 3h |
| T4 | uni-app 项目初始化 | 2h |
| T5 | 用户注册/登录页面 | 4h |
| T6 | 用户档案 + 新手引导 | 4h |
| T7 | 首页框架与样式 | 3h |
| T8 | 集成测试 + Bug 修复 | 4h |

顺序是：先数据库、再安全策略、再登录、再页面。**容器先于内容**——先把"数据放哪、谁能看"定下来，再写界面。

## 一、7 张表：一类事实一张表

表结构是 App 的骨架，改界面容易，改表结构伤筋动骨。动手前先想清楚。HOP 的 7 张表分三层：

- **核心 1 张**：`users`——用户健康档案，和 Supabase 自动管理的 `auth.users` 一对一关联。登录凭证 Supabase 管，业务档案自己的表管。
- **业务 5 张**：`daily_summaries`（每日摘要，全 App 最核心的表）、`health_memories`（AI 长期记忆，向量存储）、`conversations`（对话记录）、`workout_logs`（运动记录，含主观疲劳度和练后心情两个妙字段）、`sleep_logs`（睡眠记录）。
- **监控 1 张**：`token_usage_logs`——每次调大模型的 token 和费用。个人开发者没有财务部门，这张表就是财务部门。

拆表判据一句话：**会不会有两个"主体"（一个用户、一天）抢同一行？会，就该拆。**

`users` 表的建表 SQL（AI 生成，我贴进 SQL Editor 执行）：

```sql
CREATE TABLE IF NOT EXISTS public.users (
  id UUID PRIMARY KEY REFERENCES auth.users(id) ON DELETE CASCADE,
  created_at TIMESTAMPTZ DEFAULT now(),
  updated_at TIMESTAMPTZ DEFAULT now(),
  deleted_at TIMESTAMPTZ,

  nickname TEXT,
  avatar_url TEXT,

  age INTEGER,
  gender TEXT CHECK (gender IN ('male', 'female', 'other')),
  height_cm NUMERIC(5,2),
  weight_kg NUMERIC(5,2),
  sleep_goal_hours NUMERIC(3,1) DEFAULT 7.5,

  fitness_level TEXT CHECK (fitness_level IN ('beginner', 'intermediate', 'advanced')),
  preferred_workout_time TEXT CHECK (preferred_workout_time IN ('morning', 'noon', 'evening', 'flexible')),

  onboarding_completed BOOLEAN DEFAULT FALSE,
  last_active_at TIMESTAMPTZ DEFAULT now()
);
```

我不懂语法，但我能验收：**表里有没有业务要的每个字段**（拿着产品设想逐项对照）；**值域能不能乱填**（CHECK 约束让数据库自己拒绝非法值）；**删用户时数据怎么办**（`ON DELETE CASCADE` 连坐删除 + `deleted_at` 软删除留后悔药）。

## 二、RLS：把"各人自扫门前雪"写进数据库

健康数据是隐私。只靠前端"页面只请求自己的数据"是不够的——绕过 App 直接调接口，数据全裸奔。正确做法是 RLS（Row Level Security）：每条数据都问一句"当前登录的人是不是这行数据的 owner"，不是就拒绝，不管请求来自哪段代码。

```sql
ALTER TABLE public.users ENABLE ROW LEVEL SECURITY;

CREATE POLICY "Users can view own profile" ON public.users
  FOR SELECT USING (id = auth.uid());

CREATE POLICY "Users can update own profile" ON public.users
  FOR UPDATE USING (id = auth.uid());

-- 业务表模式一致：user_id 必须等于当前登录者
CREATE POLICY "Users can view own summaries" ON public.daily_summaries
  FOR SELECT USING (user_id = auth.uid());

CREATE POLICY "Users can insert own summaries" ON public.daily_summaries
  FOR INSERT WITH CHECK (user_id = auth.uid());
```

AI 生成很快，**真正花时间的是验证它真的生效**，两层：

```sql
-- 第一层：SQL 里模拟攻击
SET ROLE anon;
SELECT * FROM public.users;   -- 未登录：必须返回空

SET ROLE authenticated;
SET request.jwt.claims.sub = 'test-user-id';
SELECT * FROM public.users WHERE id = 'test-user-id';  -- 只能查到自己
```

第二层：Dashboard → Authentication → Policies 逐表人工核对。验收标准一句话：**未登录状态查任何业务表必须返回空。** 安全没有"大概齐"。

## 三、注册自动建档：触发器 + RLS 的双保险

这是本篇技术含量最高的设计，也是最容易搞混的地方。先看四层职责：

| 层 | 作用 |
|---|---|
| `auth.users` | 登录凭证，Supabase Auth 在 signUp 时自动创建，**前端不直接插这张表** |
| `public.users` | 业务档案，id 等于 auth.users.id，外键 CASCADE |
| 触发器 | 注册瞬间自动插一行空档案——**主路径** |
| RLS INSERT 策略 | 客户端"补档"兜底（触发器没生效时的 upsert），**不是建档主路径** |

触发器 SQL：

```sql
CREATE OR REPLACE FUNCTION public.handle_new_user()
RETURNS TRIGGER AS $$
BEGIN
  INSERT INTO public.users (id, nickname, avatar_url, created_at, last_active_at)
  VALUES (
    NEW.id,
    COALESCE(NEW.raw_user_meta_data->>'nickname', NEW.phone),
    NEW.raw_user_meta_data->>'avatar_url',
    NOW(),
    NOW()
  );
  RETURN NEW;
END;
$$ LANGUAGE plpgsql SECURITY DEFINER;

CREATE TRIGGER on_auth_user_created
  AFTER INSERT ON auth.users
  FOR EACH ROW
  EXECUTE FUNCTION public.handle_new_user();
```

四个要点：

1. **时机**：`AFTER INSERT ON auth.users`，每注册一个账号跑一次，前端零代码。
2. **`SECURITY DEFINER`**：以函数所有者权限运行，**绕过 RLS**。注册瞬间用户还没有有效登录态，建档不能依赖用户 JWT——这是设计，不是漏洞。
3. **只写四个字段**：`onboarding_completed` 走建表默认值 FALSE——新用户必走新手引导，一个跑不掉。
4. **昵称 COALESCE**：邮箱注册一般不带 nickname 也没有 phone，所以新行昵称通常是 NULL，引导结束用邮箱前缀补上。

一个真实插曲：**这份触发器脚本只活在 Dashboard 里，没进代码仓库的 migrations 目录**——后来翻代码找不到它，只能回数据库核对。建议你引以为戒，重要 schema 变更落进版本库。

RLS INSERT 策略（`WITH CHECK (id = auth.uid())`）是干嘛的？兜底。前端 `completeOnboarding` 的逻辑：先 `UPDATE` 自己那行；发现没行（触发器没装、失败、历史账号）就 `upsert` 补一条。**触发器负责"出生时建档"，RLS 策略负责"补档时不出轨"，两者不重复、不冲突。**

## 四、登录方案：被推翻的计划

W1 计划是**手机号 + 验证码**：`signInWithOtp()` 发验证码、`verifyOtp()` 验证，Supabase 提供测试号码（+1 555 555 1234，验证码固定 123456），开发期零成本。当时验收全过。

**第三周被推翻了。** 原因很实际：正式短信要么花钱接第三方、要么卡审核；内测就十几个种子用户，为十几个人搭短信链路，成本收益完全不匹配；种子用户全是熟人，邮箱注册零门槛。

于是 W3 中期改成**邮箱 + 密码**：Email Provider 开箱即用，零额外成本。内测期记得在 Authentication 设置里**关闭 Confirm email**——用户都是你自己拉的，确认邮件纯属摩擦；开放注册时再打开防机器人。

登录方案不是技术问题，是成本问题。而且 Supabase Auth 可插拔——**登录方式可以后换，数据库结构才是难改的**。前提是登录凭证和业务档案分开存（auth.users / public.users 两层结构），换登录方式时业务数据一根毫毛不用动。

## 五、"断点续填"？我差点写错的设计

新手引导五步：欢迎 → 健康档案（年龄 18-80 / 身高 100-250 / 体重 30-200，必填校验）→ 运动偏好（水平三选一 + 时段四选一）→ 数据授权 → 完成。

两个值得抄的设计：

- **第 4 步不弹系统授权。** "继续"和"稍后授权"都只是下一步；真正的 HealthKit 授权发生在引导结束后，由路由函数决定去不去授权页。授权弹窗出现在用户理解了"为什么"之后，而不是流程中间猝不及防。
- **昵称三级 fallback**：邮箱 @ 前缀（最长 20 字）→ 手机号末四位"用户xxxx" → "健康用户"。用户不填昵称，首页永远不空白。

然后是我差点写错的地方。我以为引导做了"断点续填"——填一半杀 App，下次接着填。**实际上没有，也不需要**：表单只在页面内存里，杀掉重开从第 1 步重来。五个字段重填不到一分钟，做云端草稿纯属过度设计。

真正的"断点"只有一道：**整段引导，完成/未完成。** 三道机制守着：

1. **权威字段** `public.users.onboarding_completed`：登录路由查它，false 进引导页，true 进首页；
2. **本地缓存**（按 userId 记录）：少打接口，拉档案失败时不错杀老用户；
3. **门禁**：首页、助手、训练等主页面 `onShow` 调 `ensureOnboarded()`，没完成强制跳回；已完成用户误入引导页，直接 `reLaunch` 回首页。

完整时序：

```
signUp → auth.users INSERT → 触发器插 public.users（onboarding_completed=false）
→ 登录路由 → 引导页 → 五步填写（内存表单，中途退出从头再来）
→ completeOnboarding()：UPDATE 置 true（无行则 upsert 兜底）
→（iOS 未授权）HealthKit 授权页 → 首页（各主页持续守门）
```

**要不要给引导做草稿？先问"用户重填一遍的成本有多高"，再决定。**

## 六、最后一天：测试清单是最诚实的文档

W1 最后一天不写新功能，AI 生成测试清单，我手动逐项过：登录注册流程 9 项、数据库验证 4 项（注册后 auth.users 有记录、public.users 自动出空档案——触发器在岗的直接证据、档案字段更新、RLS 跨账号验证）、UI 与性能。

个人开发者没有测试工程师：**AI 出清单，你当测试工程师。** 这个分工比让 AI 自动测试靠谱——清单可以做得非常细，而"亲手点一遍"恰恰是 AI 替代不了的。
