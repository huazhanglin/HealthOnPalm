# 第五章 第三周：换真粮——自研插件、真数据与第一次内测

第四章结尾留了个钩子：通往 HealthKit 的原生插件之路，会先被整个推翻一次。这一章兑现它——顺便讲完 W3 的另外三件事：把假数据换成真数据、一次三连的中期变更、以及第一场种子用户内测。

W3 的目标一句话：**HealthKit 真实数据同步跑通 + 手动记录 UI 完成 + 5 人以内种子用户内测。** 时间范围 Day 15–28（2026-07-29 至 2026-08-11），原计划估约 40 小时；进行中又在任务表上挂了两项计划外任务——语音约 1.5 天、改登录约 0.5 天。

这一周结束时，App 里 AI 看到的不再是编出来的步数，而是用户 iPhone 里真真实实的每一步；种子用户拿到了安装路径。这一周账上记的净投入约 21 小时，AI 参与度约 70%——比 W2 的 80% 低了十个百分点。为什么降？后文账本那节会算。

## 5.1 插件之死：W3 当周的那次推翻

先交代前情。W3 之前的路线本来不是 iOS App——更早的时候，AI 调研给出的结论是"用 DCloud 市场的第三方插件，可以在微信小程序里读取健康数据"。这个结论有个根本性的错误：**微信小程序根本不支持 HealthKit。** iOS 的 HealthKit 是 Apple 的私有 API，只在 iOS App 里可用；小程序跑在微信的容器里，拿不到这份数据。这次推翻发生在 W3 之前（书稿前面讲过"三周变四周"），发现错误的是人不是 AI——AI 在调研插件市场时只看了功能描述，没有验证"微信小程序能否访问 HealthKit"这个**前置条件**。AI 擅长整理信息，但同样擅长**相信**信息——当你需要质疑一个前提假设时，AI 的置信度和一个新手的置信度是一样的。

路线改成 iOS App 之后，W3 开工第一天（2026-07-29），轮到当周自己的决策上场：**用现成的第三方插件，还是自己写？**

AI 调研报告一开始的推荐是现成插件——方案 A，一个叫 szy-healthkit 的 UTS 插件，MIT 许可、文档完善、2026 年 7 月还在更新，看上去完美。但调研继续往深处挖，结论反转了，改判理由是三条：**市场上一部分 HealthKit 插件已经 1–2 年没更新，iOS 17+ 兼容性要自己验证；真机调试和版本兼容不够稳定；而 HOP 实际只需要 MVP 级别的读取**。调研报告把四个方案摆上了桌面：A（szy-healthkit，免费 MIT）、B（wrs-uts-health，商业插件、要私聊作者进交流群）、C（原生插件旧模式、要购买且不支持离线打包）、D（自研 UTS 插件）。最后拍板的是 D——理由是"自研的维护可控性远高于第三方插件"。

这里藏着一个"估时被执行打脸"的活教材：对比矩阵里方案 D 写的预估是 **5–8 天**；任务表上按 **8 小时** 记账；而 Cursor 实际在**同一个日历日**——7 月 29 日，调研完成的同一天——就交出了初稿：Swift 原生读取层、UTS 封装、entitlements、类型定义、业务适配层全齐。（OPC 一天就那么两三个小时，"一天交付"的说法要打个折——准确表述是"同一日历日交初稿，账记 8 小时"。）预估 5–8 天的活，8 小时干完了。这不是估时的人蠢，是**"你把任务书写清楚之后，AI 执行的下限会远超人类直觉**"——这件事每次发生，都值得记进账本。

开发回顾里那笔总账也记在这里：整个项目三次推翻 AI 的建议（小程序→iOS、第三方插件→自研、OpenRouter→SiliconFlow），合计约 8–10 小时的决策成本。**AI 擅长执行，不擅长决策。每次推翻 AI 建议，都是人在付出时间成本**——但有些成本，付了才买得到"可控"两个字。

最终的技术决策记录（ADR）定下了几条边界，值得抄：同步模式用**按需同步**，不做 Background Delivery；数据范围**只做当日**；微信小程序不接入 HealthKit（用 Mock/手动录入降级）；**Mock 回退保留**——这最后一条，后面会再见到它。有一点要说明：ADR 里设想过 onShow（打开页面）自动触发同步，**当周没做**——W3 的实际形态是授权页手动刷新，半小时自动同步、跨日同步、晨报生成前同步，都是 W4 补的。

## 5.2 插件解剖：一个人怎么"写"出原生插件

先破除迷信：自研插件不等于我从头学会了 Swift。

这个插件住在 `uni-app/src/uni_modules/health-agent-healthkit/`（W3 的实际运行对照专门标注过这个位置——不是仓库根目录，也不是调研稿里写的另一个路径）。内部是三明治结构，每一层都有明确分工：

```
uni-app/src/uni_modules/health-agent-healthkit/
├── utssdk/app-ios/HealthKitBridge.swift   ← Swift 写的原生读取层，直接调 Apple 的 API
├── utssdk/app-ios/index.uts               ← UTS 导出入口，把 Swift 包成 Promise 接口
├── utssdk/app-ios/UTS.entitlements        ← HealthKit Capability 声明
├── utssdk/interface.uts                   ← 接口契约定义
└── utssdk/types.ts                        ← 类型定义
uni-app/src/lib/healthkit/index.ts          ← 业务适配层，全 App 统一从这调
```

对前端的业务代码来说，HealthKit 的全部复杂性被压缩成四个函数：

```typescript
import { isAvailable, authorize, fetchToday, syncTodayFromDevice } from '@/lib/healthkit'

isAvailable()          // → 是否可用（仅 iOS 真机为 true）
authorize()            // → 请求授权
fetchToday()           // → 读取今日数据
syncTodayFromDevice()  // → 读取并同步到 Supabase（推荐入口）
```

**W3 结束时**，`fetchToday()` 真正读回来的是这些：步数、主动消耗能量、锻炼分钟数、站立小时数、睡眠（深睡/REM/清醒分段）、静息心率 + 平均心率、**所有运动记录**。最后这项是惊喜：Apple 的 Workout API 支持 80 多种运动类型，跑步、游泳、羽毛球、瑜伽、划船、骑马……一次查询全拿回来，每条带时长、热量、距离——距离还贴心地给了米和公里双字段。

两个诚实的脚注。其一：**插件清单里写了"基础代谢"，但 W3 当周并没有真正查询它**——字段在接口里，数据没进去。连同 HRV、血氧、呼吸频率、VO₂、爬楼，这批扩展真正写入是 W4 的事；现在的 HealthKitBridge.swift 和 sync-healthkit 都已是 W4 扩展后的版本，拿现在的代码去对 W3 会对不上。其二，W2 建 `workout_logs` 表时预留的"主观疲劳度和练后心情"字段——**HealthKit 永远不会填这两个字段，它们只属于手动记录**。真数据住进来的，是时长、热量、距离和 Apple 的 workout_id。

还有一层设计值得单独讲：**非 iOS 环境怎么办？** 答案在适配层 `index.ts` 里：`#ifndef APP-PLUS`（非原生 App 平台）直接返回"不可用"。注意，插件层**不会**自动落回 Mock——它只负责诚实地说"我不可用"；要不要用假数据兜底，是晨报和首页层的事（见 5.6 节）。一个插件只做一件事、说真话，降级策略交给上层——这是接口设计的老规矩，但在 AI 写代码的时代依然成立。

## 5.3 sync-healthkit：三张表与一次权威的 ALTER

读到了数据，下一步是送到云端。sync-healthkit 是一个 Edge Function，把当日数据写进 W1 就建好的三张表：

- **daily_summaries**：upsert 步数/热量/站立/锻炼分钟/心率/运动总数/总距离，冲突键 `user_id,date`，来源标记 `source: 'healthkit'`
- **sleep_logs**：睡眠时长/深睡/REM/醒来次数，同样的按日 upsert
- **workout_logs**：每条运动一行

但要说清楚一个容易含糊的点：**表是 W1 建的，幂等键不是。** 真正的权威变更是 `supabase/migrations/20260806_w3_sync_healthkit.sql`——这次 migration 给 `workout_logs` 加上了 workout_id 列和 `UNIQUE(user_id, workout_id)` 约束（workout_id 用 Apple 生成的唯一标识），给 `sleep_logs` 补上 `(user_id, date)` 唯一约束。W3 的数据同步，靠的是这次 ALTER，不是"直接往旧表里塞"。

为什么要这么讲究？两个新手容易踩的坑：

**坑一：睡眠是跨日的。** 凌晨 1 点睡到 8 点，算哪天的睡眠？HOP 的窗口是**昨日 18:00 → 今日 12:00**（Swift 里是从今日 12:00 往前推 18 小时），这个窗口里的睡眠统一记到今日。不做这个处理，深夜的睡眠会被撕成两半，两头都算不对。另一个要留意的现实：睡眠**分段**（深睡/REM/清醒）依赖 iOS 16+；种子用户的门槛写的是 iOS 14+——老系统上，可能只有总时长，没有分段。

**坑二：必须幂等。** 用户今天打开 App 十次，就同步十次——没有 upsert 和唯一约束，`workout_logs` 里会躺十条一模一样的跑步记录。**幂等不是优化，是这类同步功能的底线。**

另一个值得记的教训来自 SQL：T3 施工稿里 AI 顺手另写了一套建表语句，而施工稿里明确标注了"不要重复执行与现网冲突的 CREATE"——和 W1 那个只活在 Dashboard 里的触发器是同款问题，反过来了：这次是代码里多了一套"影子 SQL"。**数据库结构变更只有一个权威来源，就是 migrations 目录。**

W3 当周的同步形态再说一遍：**以授权页手动刷新为主**。ADR 里设想过的 onShow 自动触发、后来的半小时自动同步、跨日同步、晨报生成前同步，都是 W4 才有的。W3 的用户每次要看新数据，得自己去授权页点一下刷新——不优雅，但真机跑通了，先跑通，再优雅。

## 5.4 授权：Apple 设的一个"坑"

HealthKit 的授权流程有个反直觉的设计，值得单独开一节。

正常的想象是：用户点了"拒绝授权"，App 里 `authorize()` 返回 false，一切清清楚楚。实际呢？**Apple 的读权限没有明确的 denied 状态**——用户拒绝了授权，查询不会报错，只会返回空数据。你的代码永远无法确定"用户拒绝了"还是"用户健康 App 里本来就没数据"。

这个设计的哲学是隐私优先（App 不该知道用户拒绝过什么），但对开发者是实打实的坑：按错误状态做分支处理的代码，在这里全部失效。调研报告风险表里那句很冷静的话就是应对方案：**"读权限无明确 denied，以能否读到数据为准"**——不做无谓的状态推断，读到了就用，读不到就回退。

前端授权页的流程：首次打开或从"我的 → 数据同步"进入 → 说明权限用途与隐私保护 → 主按钮"授权健康数据"→ 成功则自动触发一次同步，把 `hasHealthKitAuth` 记进本地缓存；失败/拒绝则显示"授权未完成"+ "稍后授权"按钮——**永远给用户留一条"稍后"的路**，不逼授权，这和引导第 4 步不弹系统授权是同一个克制原则。（后话：现行 authorize.vue 的 onShow 里已经带上 W4 的半小时定时同步和 ensureTodaySynced 了——那不是 W3 的样子。）

真机调试还有两个环境坑，记录在案：第一，HBuilderX 必须装 **App 版**（Vite CLI 的 dev:h5 无法验证 HealthKit），要走"自定义基座 → 真机"这条路，且 App ID 必须勾选 HealthKit、重签 Provisioning Profile；第二，**测试机的"健康"App 里得有历史数据**，否则读出来全是 0——不是 Bug，是你真的没走几步。还有一条 W4 踩坑后补的经验：**自定义基座用开发证书，TestFlight 用发布证书**，两套证书搞混，打包环节能折腾掉你一晚上。

## 5.5 中期变更三连：2026-08-07

W3 进行到一半（8 月 7 日，按计划自己的日历算是 Day 24），发生了一次集中变更——三件事同一天记录在案。前两件第三章埋过伏笔，这里兑现。

**变更一：登录改为邮箱 + 密码。** 手机号验证码方案正式退场，理由第三章讲过：短信通道的成本与审核，对十几人的内测完全是高射炮打蚊子。旧手机号会话不再作为主路径，种子用户用邮箱重新注册。W2 计划也补了一行修订说明，防止"历史计划原文"日后误导。

**变更二：HOP 助手长了嘴和耳朵（计划外加分）。** 语音输入 + 语音播报，原计划里没有，中途挂上任务表的（约 1.5 天），实际完成它：

- **语音输入**：按住"语音"录音 → speech-to-text（SiliconFlow 的 SenseVoice）→ 转写文本填入输入框
- **语音播报**：点助手气泡上的"播放" → text-to-speech（CosyVoice2）→ 音频存进 Storage 的 `tts-cache` 桶 → 前端拿签名 URL 下载播放

注意这里的一个工程巧思：**语音合成结果做了缓存**（tts-cache 桶）。同一段回复播第二遍，直接取缓存的音频，不再花一次合成费用——又是那个贯穿全项目的主题：token 和推理，都是真金白银，能省则省。配置层面，manifest 要启用 Record、Audio 原生模块，iOS 要声明 `NSMicrophoneUsageDescription`（麦克风用途说明，App Store 审核必看）。

**变更三：种子分发定为 TestFlight。** 远程用户装 App 的路径：已有的 Apple Developer **付费**账号 + TestFlight 内部测试。两条歧路被明确排掉——微信小程序体验码（根本测不了 HealthKit）和自定义调试基座（只有开发者本机能装）。

一天之内三连变，恰好是个人开发者的常态：**计划是地图，用户反馈和现实条件才是方向盘。** 和"三周变四周"那次被迫返工不同，W3 的变更是有准备的变更——每一条都有原因、有现状、有代码位置、有兼容说明，落进文档，随时可查。

## 5.6 手动记录与 Mock 回退：真数据的备胎

接了真数据，为什么还要做手动记录？因为真数据有缝隙。

Apple Watch 没戴、手机忘在桌上、"健康"App 本来就是空的——这些情况下 HealthKit 读到的就是零或空。用户练了一小时力量，手表没记上，难道这堂课就不算数？所以 W3 做了两块手动记录 UI：**运动记录页**（手动记 + 查历史）和**睡眠记录页**（手动补充）。W2 预留的"主观疲劳度/练后心情"字段，也在这里等着用户自己来填。

但手动数据和自动数据怎么共存，答案比"合并成完整图景"要现实：**按日摘要和睡眠是覆盖，运动是按条去重追加。** sleep_logs 有 `(user_id, date)` 唯一约束、按日 upsert——同一天先手动填了睡眠、又触发同步，同步会整行盖掉手填的，不是两条睡眠拼在一起。运动记录可以并存：HealthKit 的记录靠 `(user_id, workout_id)` 去重，手动记录的 workout_id 是空（Postgres 允许多个 NULL），各记各的、一起展示。**设计里没有魔法，只有约束——先想清楚谁覆盖谁、谁和谁并存，再让 AI 写代码。**

Mock 回退也在这一周正式上岗。有意思的是它的口径变化：任务稿最早写过"回退时**用户无感知**"——静默兜底；上线时的实际产品是**首页必须有来源徽标**：真实 / 模拟 / 混合，标得清清楚楚。计划阶段想过偷偷用假数据糊弄过去，做的时候自己推翻了自己：宁可告诉用户"这段简报基于模拟数据"，也不冒充真实。种子内测说明里连体验预期都写明白了："若'健康'App 里本身几乎没有数据，同步结果可能偏少或显示模拟补充——属正常现象。"

晨报也多了反馈机制：每条建议可以点**采纳 / 忽略 / 修改**——这三个按钮是给 W4 和 V1.0 的礼物：用户的每一次选择，都是"AI 说什么样的话才有用"的第一手训练素材。此时它只是个按钮，价值要过几周才显现。

## 5.7 第一批用户：种子内测

W3 的收官任务是把 App 交到第一批真人手里。目标人群：5 人以内的熟人小圈子，**必须持有 iPhone（iOS 14+）**——不是苛刻，是 HealthKit 只在 iOS 上活着。

内测材料的情况要说准确：真正落成文件的是两份——**《种子用户内测说明》**（文件版本 v0.1，文内标注 v0.2）和**反馈追踪表**（模板）。筛选标准、分发方案、问卷题目，则是 W3 计划里 T8 章节的内容，没有单独成稿。里面有个筛选标准值得单独说：**"不是核心熟人"——避免人情干扰反馈的真实性**。太熟的朋友不忍心说难听话，而内测要的恰恰是难听话。名单建议的构成也讲究：1–2 名有运动习惯的、1–2 名关注健康但不怎么运动的、1 名有产品或技术背景的——各取所需，各挑各的毛病。

内测说明（v0.2）给种子用户设计了一条 20–25 分钟的七步体验路径：装 App → 注册 → 填档案 → 授权 HealthKit（"重要"标记，5 分钟）→ 看晨报并点一次采纳 → 问 AI 一个问题（试一次按住说话、试一次播放）→ 反馈。

反馈问卷有两套口径，这里如实分开记。**计划 T8.1 材料包的问卷是六问**：简报有没有用（1–5 分）？AI 回答准吗？语音好用吗？**数据从哪来的？**最想要什么功能？最大痛点是什么？——第四个问题是埋的钩子，它是来检验"来源徽标"有没有做明白的：用户如果答"不知道数据从哪来"，说明诚实标识做得还不够醒目。**内测说明 v0.2 第 5 节自己建议的问卷是七题**：没有单独问语音的，数据来源排第 3 题，第 6 题是"还会继续用吗"——两套问卷到 W3 结束都没有合并定稿，问卷链接在文档里还是"〔待填写〕"。

然后是这一章必须诚实交代的结局：**W3 结束时，开发者自己的 TestFlight + 真机路径完全跑通了；但正式的 3–5 人种子反馈，没有归档**——仓库里那份反馈追踪表，直到今天仍是空模板。验收清单上，工程项全勾，种子运营两项是空的。

为什么会空？回头复盘，W3 的实际重心不可避免地倒向了工程侧——插件推翻、中期变更、真机调试，每一件都在抢时间；到了分发阶段，人已经疲了。这是单人项目的经典陷阱：**开发和运营用的是同一份精力，开发永远有下一个 Bug，运营永远可以"明天再说"。** 所以这一章的检查清单里，"发出去"被列成了和"跑起来"同级的验收项——产品没到用户手里，就不算做完。

## 5.8 W3 里程碑：验收，与一笔不能算错的账

先看验收。官方清单的 P0 其实是**八项**——工程六项 + 种子运营两项，这里拆开写：

**工程 P0——六项全过：**

- [x] HealthKit 数据同步（iOS 真机测试通过；W3 以手动刷新为主，自动同步在 W4）
- [x] 数据质量评估 + Mock 回退逻辑
- [x] 手动运动/睡眠记录 UI 完成
- [x] 晨间简报反馈机制
- [x] 邮箱 + 密码注册/登录
- [x] HOP 助手语音输入 + TTS 播报

**种子运营 P0（官方清单也把它们标成 P0）——未完成：**

- [ ] 3–5 名种子用户经 TestFlight 完成首次体验（开发者已通；多人未归档）
- [ ] 种子用户反馈报告（追踪表仍为空模板）

**P1（可选）大部分完成：** 运动历史周视图 ✅、睡眠历史周视图 ✅、数据来源标识 ✅、语音体验可持续打磨 ✅、种子 DAU 监控 ❌。

然后算账——这笔账有几个数字放在一起会互相打架，得摆清楚。

原计划估约 40 小时。中期任务表上又挂了两项计划外的活：语音约 1.5 天、改登录约 0.5 天。而开发回顾里，W3 整周的**净投入约 21 小时**，分项是：调研 3 + 插件 8 + 数据同步 3 + 授权 UI 2 + 运动类型 2 + 内测 SOP 3。

发现问题了吗？**分项里没有单列语音、改登录、手动记录、Mock 回退、晨报反馈**——这些计划外的活，被揉进那 21 小时里了。同时，"1.5 天"是任务表的写法，OPC 是晚上干活的，一个"天"不等于八个工时。所以这笔账**不能**读成"计划 40 + 计划外 16，结果只干了 21"——正确的读法是：**计划约 40h，中途加活，最后一周净投入 21h，其中相当一部分是计划表上原本没有的事。** 估时和记账是两套口径，OPC 的账本永远以净投入分项为准。

AI 参与度约 70%，比 W2 的 80% 低了十个百分点。降低的原因不能全算在"决策"头上：插件那 8 小时依然是 AI 主力；真正把人的占比抬上来的，是**调研核实、真机证书、HBuilderX、自定义基座**这些必须人手把手干的活。三次推翻合计 8–10 小时的决策成本是**全项目**的总账，不是 W3 一周的。准确的图景是：W3 的人机分工从"AI 写、我审"变成"AI 写、我审、我还要去按真机上的按钮"。

开发回顾里 W1–W3 的累计账：5 周、净投入约 46 小时、AI 平均参与约 73%。**一个人的五周，加上 AI，做出了一个能装进别人手机里的产品。**

W3 结束时的 App 长这样：底部三个 Tab（首页 / 记录 / 我的——五 Tab 是 W4 的事）；晨报基于真实数据（带来源徽标）；可以打字也可以说话地和 AI 聊天；用户说明书 v1.0 已于 8 月 8 日写好。它已经是一个"产品"的形状了——只是还没经过陌生人的手指。

## 常见问题

**Q：AI 调研报告推荐了现成插件，我为什么不信？**
不是不信 AI——AI 的调研信息基本准确，szy-healthkit 确实存在、确实在更新。问题在**判断**：真机调试和版本兼容的稳定性、商业插件的沟通成本、停更风险，这些对"健康数据是这个 App 的命根子"的项目意味着什么，AI 不知道——它不知道你的项目命脉在哪。所以正确姿势是 AI 原则里那条：**AI 给选项列表（不做决策，只整理信息），人做决策（基于约束清单和长期目标），AI 执行被选中的方案。** 调研报告的四方案对比矩阵就是"选项列表"的理想形态。

**Q：自研插件预估 5–8 天，账记 8 小时，同一日历日交初稿——我还怕什么原生开发？**
怕的前提已经变了。你要写的不是"Swift 插件"，是**给 AI 的一份精确任务书**：读哪几类数据、睡眠窗口怎么切、什么平台返回不可用、幂等键是什么。这些想清楚了，Swift 对 AI 不是障碍。想不清楚，AI 一天也能给你写出七份"看起来对"的文件。原生开发真正难的从来不是语法，是 HealthKit 那些设计哲学——比如读授权状态不可信。

**Q：我的 App 是 Android 的，这章还有什么用？**
三样东西是跨平台的：**按需同步 + 当日范围**的边界设计（别一上来就做 Background Delivery）；**幂等 upsert**（Google Fit 同样会重复回调）；**"读不到数据"和"用户拒绝"不可区分**的坑（Android 权限系统对 Health 类 API 有类似设计）。以及那句最通用的：第三方 SDK 的停更风险，靠自研或靠"仅依赖不可替代部分"来化解。

**Q：种子用户找熟人，会不会全是人情分？**
所以要"半熟"——认识、但没好到不好意思说真话；所以在问卷里埋"数据从哪来的"这种诚实测试题；所以名单里刻意配"关注健康但不运动"的用户——他们没有运动习惯可以原谅产品，只会用普通人视角挑刺。**内测收不到负面反馈，是最贵的假阳性。**

**Q：W3 的种子反馈空着，算失败吗？**
算未完成，不算失败——区别在于工程链路（TestFlight 打包、内测说明、追踪表模板）全部就绪，缺的是"按下发送键"这个动作。而且要如实说：W4 也没有先去填它——那一周先修了真数据进来之后暴露的产品问题。这不妨碍教训成立：**"跑通"和"发出去"是两条验收线，跨过第二条，产品才算离开产房。** 这条债挂账在册，早晚要还。

---

第三周结束，App 第一次吃上了真粮——AI 说的每句话背后，是你真实的步数、真实的睡眠、真实的心跳。但真数据一进来，新的问题跟着进来：数据太干净时是故事，数据连续、杂乱、有缺口时，才是生活。

第四周要面对的，就是生活本身：恢复分算法整个重做、自动同步补上、五 Tab 和动作库训练闭环登场。至于那份空着的反馈表——W4 也没顾上填它，因为真数据暴露出来的问题，比问卷更急。那一周的净投入 25 小时，是四周里最高的：**做对一件事，比做多一件事，贵得多。**
