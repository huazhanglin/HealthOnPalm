# 第七章 第五周：文档周，以及一份可带走的 OPC 清单

> 本章分上下两截。**上半写第五周**：这三天（2026-08-24 至 08-26）为什么必须停下来写对——真相债、对照表、对码、一笔没还的 git 债。**下半是全书小结**：把七章里反复出现的问题收成一张图、七条规矩和一笔总账（按冻结日 2026-08-26 写）。**末尾是展望**：产品还欠什么、这本书把读者送到哪。

前六章把 App 从一个想法做到了能转的闭环。第五周没有新功能。第六章结尾埋了两颗雷——TabBar 的 redirectTo 要换成原生 tabBar，反馈追踪表要发出去填——**按剧本，第五周该拆雷了。结果一颗都没拆。** 底部导航还是那个 HomeTabBar.vue；追踪表还是空模板；Sleep Insight、Weekly Review、血压、支付、上架材料——W4 预告的每一项，一个都没开工。App 停在约 0.3.8 / versionCode 138：没有一行产品代码、没有一条新迁移、没有一个新的 Edge Function。

那这三天干了什么？干了另一件事，一件写代码的人容易看不起、但比代码更急的事：**把 W1–W4 对成"实际发生过的事"，写成可对外讲述的书稿。**

这一章如果你期待新功能、新技术，上半可以跳过——但如果你想独立做产品，这一章讲的可能是全书最容易被忽视的一类债：**不是功能债，是"真相债"。** 你的计划文档、你的记录、你的仓库，和实际发生的事对不上——拖得越久，利息越高。

## 上：第五周——把发生过的事写对

## 7.1 施工稿的保质期：一本会撒谎的说明书

问题的暴露很偶然。写这本书第三章（W1）的时候，我把 W1 的详细执行计划翻出来当素材——然后发现**它是一本会撒谎的说明书。**

它的正文写的是：**微信小程序**、微信登录或手机号 OTP、Supabase 后端。而真实交付的是：**iOS App、邮箱密码登录**——注意，后端从一开始就是 Supabase，从头到尾没换过；**对不上的只有"端"和"登录"这两样。** 这不是谁的错——W1 中途改了技术路线，计划文档记录的是"当时的打算"，本来就不是"后来的事实"。问题在于：**这份文档没有任何标记告诉你它过期了。** 未来的自己（或者一个照着它学习的读者）打开它，会认认真真地按"小程序 + 微信登录"去施工——一厢情愿地走向一条已经废弃的路。

W2、W3 的计划同样带着这类暗伤：W2 计划里训练闭环写得像当周要交付，实际 W4 才做；W3 计划里基础代谢列在插件清单里，实际当周根本没查。**计划文档的保质期，比大多数人以为的短得多。** 决策一变，计划就变成了过期地图——过期地图不可怕，可怕的是它看起来还像新的。

怎么处理？W5-T1 给出了一个值得抄的模式：**不改历史正文，在文首加一张"实际运行对照"表。**

| 文档 | 对照要点 |
|---|---|
| W1 计划 | 主端是 iOS App 不是小程序；登录是邮箱密码不是微信/OTP；代码在 uni-app/ |
| W2 计划 | 晨报 + Agent 已真机跑通；无定时推送；Workout 是文案级；恢复分细则在 W4 重做 |
| W3 计划 | 插件路径在 uni-app/src/uni_modules/；当时是三 Tab；基础代谢当周未查；自动同步在 W4；种子表空 |

三条对照还特意写明两句硬话：**微信小程序不是交付物**（防止读者照着废案走）；项目 ref 是 zewznptbyhurxaqirzmb（防止对照表本身又变成模糊表述）。验收标准也定得干脆：**"以对照为准，而非过期的 Day 任务"**——历史正文留着当施工记录，现状以对照表为准。**文档不必涂改历史，但必须声明现状。**

W4 的记录不用做这一层——因为它本来就是"执行记录"体裁，写的就是发生过的事。这也顺手立了一个规矩：**计划文档和执行记录是两种东西，前者是意图，后者是事实；意图允许落空，事实不允许掺水。**

## 7.2 对码：给书稿做一次事实核查

W5 的第二件事（T2），起因更具体：书稿要写触发器、要写新手引导、要写 Mock 规则、要写恢复分公式——**每一个细节都可能在"凭印象写"的时候写错。** 于是按仓库逐条核对，术语叫"对码"。核对出来的硬规则，这里拣几条出来看看"印象"和"事实"能差多远：

- **注册建档**：印象里"注册时往 users 表插一行"。事实是：前端 `register()` 只做 signUp，**不直接 insert**；插行的是数据库触发器 `handle_new_user()`（SECURITY DEFINER），挂在 auth.users 的 INSERT 上。而且触发器的 SQL 在 W1 的 T2.3 任务和 Dashboard 里，**不在 supabase/migrations/**——找错地方会以为它不存在。
- **嵌入维度**：W1 建表时 `content_embedding` 是 VECTOR(1536)；后来切到 SiliconFlow 的 bge-m3 模型，ALTER 成了 1024。书里如果只写一个数，就有一个周份的错误。
- **新手引导**：五步——欢迎 → 健康档案（年龄/身高/体重）→ 运动偏好 → 数据授权（**这一页不调系统弹窗**）→ 完成。没有云端草稿：中途杀掉 App，从欢迎页重来，不是断点续填。
- **记忆窗口**：对话记忆 MAX_MESSAGES = 20，摘要阈值 SUMMARY_THRESHOLD = 12。凭印象写会变成"保留最近若干条"这种永远不错也永远没用的表述。
- **供应商切换**：OpenRouter → SiliconFlow 发生在 W2 部署时——不是 W1 就选对了。

对码的成果不止挂在第六章：**第五、六章的 v2 是改得最密的两章**，三、四章的口径（触发器位置、插件路径、W3 没查基础代谢、睡眠覆盖与运动追加的区分）也在这轮核过。第六章 v1 写完之后，逐条对照代码和记录，改出了一批硬错，例如：**exercise_ids 列不是 W2 预留的，是 W4 建动作库时才加的**；心情写死 normal 按 W2 公式是 5 分，不是 8 分；LLM 的围栏是 160 条 featured，不是 860 条全库；P0 第九项是"SQL 已执行"，不是说明书。每一处单看都是小事，堆在一起就是一本书在系统性地教读者错误的事实。**给读者看的技术叙事，每个名词、数字、日期都值得回仓库对一遍——对不上的，宁可删掉。**

## 7.3 证明"没做"，也需要证据

W5 记录里有一节很特别：**产品侧核对——用仓库状态证明"W4 预告的 W5 一项都没做"。** 2026-08-26 复查的结果，全部与 W4 结束时相同：

| 检查项 | 状态 |
|---|---|
| 底部导航 | HomeTabBar.vue **函数名叫 switchTab，实现是 uni.redirectTo** |
| 原生 tabBar | pages.json 无 tabBar 配置 |
| 数据库迁移 | 最新仍是 20260821_healthkit_recovery_metrics.sql（W4） |
| HealthKit 类型 | 无血压；临床类仍不读 |
| 种子追踪表 | 用户行空白 |
| git | 仅 13263c5 一个 commit（2026-08-10，W1–W3）；其后全部在工作区 |

第一行值得单独说，而且要说准确：**HomeTabBar.vue 里那个 `switchTab` 是组件自己的本地函数名，不是 uni-app 的 `uni.switchTab` API**——名字先改了，实现还是 redirectTo。名字先到了，实现还没跟上——这是单人项目里最典型的"半截工程"：动手的人知道差在哪，看名字的人（包括两个月后的你自己）以为已经做完了。如果 W5 不做这次核对，两周后连开发者自己都可能被这个名字骗过去。

这一节的方法论朴素但少见：**"没做"不能靠记忆声明，要靠证据立案。** 个人项目里顺延是常态，顺延了什么、顺延到哪、当时仓库是什么状态——不记下来，三个月后就变成"好像做过又好像没做过"的罗生门。这和第六章"砍掉的任务也要有清单"是同一个原则的另一面：**做过的要有验收，没做的要有立案。**

## 7.4 13263c5：一个只有一个 commit 的仓库

上一节的最后一行，是 W5 暴露出的最重的一笔债。

这个项目的 git 仓库，从始至终只有一个 commit：13263c5，2026-08-10，覆盖 W1–W3。**W4 全部的产品代码、W5 全部的文档和书稿——都躺在工作区里，一次都没有提交。** 写下这段话的 08-26 距离那个 commit 约 16 天——两周多。这个仓库的"历史"，停在两周多以前。

不是不会提交，是顺序错了。W4 那十二天被任务表推着走，"先做完再统一提交"是当时的心声——然后就没有然后了。风险不玄乎，就两条：

- **没有版本历史，就没有后悔药。** 这两周改坏过什么、改对过什么、哪次改动引入了时区 bug——全都无法回溯。万一哪天误删了文件，工作区就是唯一的副本。
- **没有提交纪律，就没有交付边界。** "做完了"的定义被模糊掉了：代码写完算做完？真机验证完算做完？还是提交入库才算？一个从不 commit 的仓库里，"做完"只是心情。

给零基础读者的翻译：**git commit 不是给团队用的仪式，是给未来的自己写的存档点。** 打游戏的人都知道 Boss 战前要存档——W4 那种一周改十一个任务的 Boss 战，居然一个存档点都没打。所以 W6 候选清单的第一行，不是 tabBar，不是扩面，而是：**把 W4 起未提交的代码与文档入库，避免唯一 commit 永远停在 W1–W3。** 过程债排在产品债前面——因为它护住的是所有其他工作的本体。

## 7.5 账本：没有数字的一周

## 下：全书小结——七章，一张问题图（冻结日：2026-08-26）

上半说的是"第五周干了什么"。下半要回答另一个问题：**回看这七章，值得带走的是什么？**

不是功能清单——功能会重写、会被推翻、会在下个版本里换样子。值得带走的是**问题**：每一章真正撞上的，从来不是"哪个 API 怎么调"，而是"作为一个人，怎么和 AI 一起把事情做对"。把七章的坑收成一张表：

| 章 | 撞上的问题 | 可带走的结论 |
|---|---|---|
| 一 | 不会写代码的人，要做一个能用的 App | **人定约束，AI 执行** |
| 二 | 模型会自信地给错方案 | **交叉评审；在纸上推翻，比在代码里推翻便宜** |
| 三 | 计划小程序/OTP，交付 iOS/邮箱；触发器不在 migrations；配置是 AI 的盲区 | **容器先于内容；权威来源只有一处** |
| 四 | 先上真传感器会耗死项目；OpenRouter 国内不可达；1536→1024；Safety 不能只靠正则 | **Mock 先行；基础设施要人验证；文档先行少走弯路** |
| 五 | HealthKit 小程序不可达；第三方插件 vs 自研；读权限无 denied 回执；种子表空 | **人验证前置条件；没发出去就不算做完** |
| 六 | 昨天的数据、redirectTo、恢复分三桩冤案、证书混用、W4 预告 V1.0 没走 | **做对先于做多；砍掉的任务也要有清单** |
| 七 | 计划会过期；印象会写错书；git 停在 W1–W3 | **对照不涂历史；对码；没做要有证据；commit 是存档** |

从这张表里，把全书反复出现过的规矩收成七条——**没有一条是新发明的，每一条都在前面某一章用代价换来的：**

1. **AI 给选项，人做决策。** 三次推翻（小程序改 iOS、第三方插件改自研、OpenRouter 改 SiliconFlow），合计花了约 8–10 小时——但每一次推翻都比将错就错便宜。
2. **计划是地图，执行记录是轨迹。** 意图允许落空，事实不允许掺水；过期地图不可怕，可怕的是它看起来还像新的。
3. **先假数据，再真传感器。** Mock 让逻辑先转起来，真数据只负责暴露 Mock 糊弄过去的问题。
4. **克制写在"不做什么"上。** 不诊断、不给组数重量、不读临床数据——一个健康 App 的边界，不在功能列表里，在拒绝清单里。
5. **同一份计算，只许存在一份代码。** `_shared/recovery.ts`：两个函数各算各的恢复分，迟早改一处忘一处。
6. **"跑通"和"发出去"是两条验收线。** 这个项目至今只跨过了第一条——闭环在转，但只在开发者自己的手机上转。
7. **账本和 git 都是写给未来的自己。** 有数字记数字，没记就写没记；做完要入库，否则"做完"只是心情。

### 总账

按开发回顾的口径（截至冻结日 2026-08-26，不新编数字）：**约 6.5 周，净投入约 71 小时**——W1 8h → W2 17h → W3 21h → W4 25h，W5 无分项；**AI 参与度约 73%。** 金钱成本约 **¥80 级**的 API 调用，基础设施全在免费层。

产品停在约 **0.3.8 / versionCode 138**：五个 Tab、真数据晨报、训练打卡闭环、心情进恢复分、缓存与自动同步——一个能转的闭环，**但主要还只在开发者自己的手机上转。**

最后，两个"还没发生"，写进总结比藏着更诚实：**陌生人种子反馈一份未归档（追踪表至今空白）；唯一 commit 仍是 13263c5。** 这本书没有讲完一个"一个人五周做出 App"的爽文——它讲的是一个人五周把闭环做对、并且如实记下哪里还没做。**承认未完成的部分，也是这套方法的一部分。**

## 末：展望——三层债，不打包票

W4 预告过 V1.0，W5 一项没做；这一章的展望不再犯同一个错——**下面是候选清单和排序原则，不是下周剧透。** 债分三层：

**过程债（不依赖任何人，只依赖你打开终端）**

- **入库。** 把 W4 起未提交的代码与文档 commit 进去。这是唯一不依赖用户、不依赖苹果审核的一项——书里已经把它写成 P0，**不做完这一项，这一章写的教训自己先打脸。**

**产品债（用户能撞上的墙）**

- **原生 tabBar + switchTab**，彻底告别 redirectTo 闪页。
- **把 TestFlight 链接发给真人，开始填追踪表。** 说清楚现状：不是"五个用户的后续"——是那张表**还是空的**，一个真实名字都还没有。扩面不是增长动作，是"第一次听到难听话"的动作。

**能力债（可以再晚，各有各的"还不到时候"）**

- **Sleep Insight Agent**——睡眠数据能稳定进来之前，洞察是空中楼阁
- **Weekly Review Agent**——日闭环交给真人跑稳之前，周报没有地基
- **血压等生活方式指标**——仍然避开临床数据这条线
- **支付/订阅**——仍免费内测，没有值得收费的用户规模
- **上架材料**——缺的正是上面那条：真实种子反馈

三层之间的顺序原则，七章里反复出现过的那句：**先拆用户会撞上的墙，再开新的能力；而在拆墙之前，先让仓库配得上"做完了"三个字。**

**第五周方法论：**

- [ ] 每份"计划"文档的文首，都有一张注明日期的"实际运行对照"表
- [ ] 对照表写明废弃方案（如"微信小程序不是交付物"），而不只是写现行方案
- [ ] 书稿/对外叙述里的每个数字、函数名、日期，都能在代码或记录里找到出处
- [ ] "当时公式"和"现行公式"分开写（如恢复分心情档：W2 是 10/7.5/5/2.5，W4 是 10/9/8/4）
- [ ] 顺延项有立案表：顺延了什么、核对日期、当时仓库状态
- [ ] git commit 覆盖到最近一次交付（工作区里没有"做完但没提交"的大块工作）
- [ ] 账本允许出现"没有数字"的行——但只有真的没记，才能写"没记"
- [ ] 验收清单里允许有未打勾的框——前提是每一框都知道为什么没打勾

**全书级：**

- [ ] 问题图谱的每一行，都能在对应章节找到出处
- [ ] 总账的每个数字，都能在开发回顾里找到，没有新编
- [ ] 展望里的每一项，都没有被写成"已完成"或"下周一定做"

## 常见问题

**Q：一周不写代码，算不算浪费了一周？**
看产出。这一周的产出是：三份计划不再撒谎、六章书稿的事实经过核查、一个只值一行的 git 状态被立案、所有顺延项有了带证据的清单。对一个还没有外部用户的产品，**让"发生过的事"保持可查，和让新功能跑起来，价值是同一种**——前者甚至更保值，因为功能会重写，而记录错了会一直错下去。真正浪费的，是既不写代码也不做对账的那一周。

**Q：为什么不改掉计划文档里的过期内容，而要在文首加对照表？**
两个原因。其一，计划文档是**决策记录**：W1 当初为什么想走小程序、后来为什么改道 iOS——删掉正文，这段决策史就没了。其二，改写历史会让文档的"口吻"混乱：一段写着"我们决定用微信登录"，下一段写着"我们用了邮箱"，读者分不清哪个是当时的判断哪个是后来的事实。**保留正文、文首加对照，等于给文档加了一层时间戳——历史归历史，现状归现状。**

**Q：对码是不是太较真了？读者不会逐字核对的。**
读者不核对，但读者会照做。书里写"exercise_ids 是第二周预留的"，读者做自己的项目时就会学着"提前预留列"——一个不存在的最佳实践，就这么传下去了。技术叙事的错误和代码的 Bug 性质相同：**作者 debug 一次，胜过一千个读者各自撞墙。**

**Q：单人项目，提交 git 有多重要？没有协作对象，commit 给谁看？**
给两个"未来的自己"看。三个月后的你想知道"这个函数是哪次改的、为什么改"——没有历史，只能重读代码考古；某天误操作删了东西——没有 commit，工作区就是唯一副本。**单人项目的 commit message 才是最纯粹的读者：写给一个和你有完全相同上下文、但已经忘光了的人。** 这个项目用"唯一的 commit 停在两周多以前"实证了这条教训。

**Q：渠道稿（公众号/掘金）和长篇书稿，为什么要分两次对齐？**
因为它们改动的节奏不同。长篇是事实的最终底本；渠道稿是长篇的"翻译"——翻译可以晚定稿，但不能自己发明事实。所以流程是：长篇先对完代码（v2），渠道稿再对长篇。跳过第二步，就会出现"公众号说 860 条、掘金说 160 条、书里说 featured 160"三个口径并存的惨案。**事实只有一个底本，所有渠道稿都是它的下游。**

**Q：照这本书做完一遍，我的 App 就能上架了吗？**
还不能，而且书里没打算教到那一步。跟着这套方法走到第七章，你能得到的是：一个**能转的 MVP 闭环**——数据进来、分数算出、计划生成、打卡回写，账目和记录如实。距离上架还缺至少三样：**真实种子的反馈**（追踪表还是空的）、**原生导航**（tabBar 还没换）、**上架材料与隐私标签**。这本书教的是"把一件事做对到可以交给第一个陌生人"，不是"做到商店里见"。**从闭环到上架之间那段路，得用真实用户的难听话铺。**
