# 第六章 第四周：做对——训练闭环、恢复分重写与那只"昨天"的幽灵

第五章结尾说：真数据一进来，数据太干净时是故事，数据连续、杂乱、有缺口时，才是生活。第四周（W4）面对的就是生活本身——**不是一周新冒险，而是对前三周所有功能的一次总清算。**

W4 的驱动源不是新点子，是一张问题清单。来源很朴素：开发者自测 + 那几个装上 App 的种子用户的只言片语。清单不长，但每一条都戳在"真数据住进来之后"暴露的伤口上：

- 底部只有三个 Tab，训练计划和 AI 助手的入口藏在二级页里，找不到
- Workout Agent 只会说"建议适度训练"，没有动作清单，没有打卡——建议完就完了，像放完烟花就散场
- 恢复分的心情维度写死 normal——用户疲不疲惫，App 根本不问
- 没有真实睡眠时，恢复分要么被打成 0，要么被 Mock 时长糊弄——一个数字两种冤枉
- "练 7 休 2"的人，训练日休息维直接 0 分——越自律，分越低
- Tab 切回首页就全量刷新，体感慢
- **早上打开 App，显示的还是昨天的数据**——一只"昨天"的幽灵
- 基础代谢字段一直空着、距离只算 Workout、说明书还是三 Tab 的老黄历

W4 的任务表 T1–T11，全部从这张清单翻译而来。执行记录的日期从 2026-08-12 一直写到 **8 月 23 日**——开发回顾里这一周记作 1.5 周；执行记录的日期跨了十二天。两套都算数：**个人开发者的"周"，是记账单位，不是物理单位。**

## 6.1 动作库：让 AI 只能点菜，不能发明菜

先做一个对账：开发回顾里说 W4"没有新的大模块"——这话和本节不矛盾。回顾指的是**没有接入新的数据域**（不像 W3 那样开 HealthKit 新大陆）；动作库是自建的新表加 Workout Agent 的重写，工程量不小，但性质仍是"把已有闭环做实"。

W4 最大的一块新工程，是把 Workout Agent 从"文案建议"做成**真正的训练闭环**：精选库出题 → LLM 只许选 ID → 写入当日计划 → 用户打卡。

先说数据。动作库的来源是 **wger**——一个开源健身数据项目（CC BY-SA 许可）。全量约 **860 条**已审核动作进了自建的 `public.exercises` 表，其中约 **160 条**标记 `is_featured`，专供 AI 出计划用。为什么不客户端直连 wger？因为要让"AI 出题"可控，数据必须先过自己的库：中英文名称、分类、阶段（热身/正式/拉伸）、强度、肌群、器械、是否徒手、配图、**署名字段**——开源协议要求的，一条不落。

然后是这一节真正的主角，那条产品规则：

**LLM 只能从候选清单里选动作 ID，禁止编造。** 注意围栏的精确范围：库里有 860 条，但 Agent 调用时传的是 `featuredOnly: true`——**LLM 只能在约 160 条精选动作里点菜，不是在 860 条里自由发挥。**

这一条规则，加上强度闸门——恢复分 < 50 或建议为 `rest` 时，只许出 light/热身/拉伸；50–80 出 light/moderate 为主；> 80 正常强度——构成了整个训练闭环的骨架。计划结构固定：热身 1–2 个 + 正式 3–5 个 + 拉伸 1–2 个。计划生成后缓存进当日 `daily_summaries.ai_plan`，可强制重新生成。

还有一个新手容易忽略的边界：**计划不给具体重量、组数、次数。** 不是做不到，是不该做——一个非医疗的健康 App，把"练多重练几组"写死给用户，出了事说不清。给到动作、顺序、强度档位，剩下的让用户自己拿捏。**克制不是功能少，是知道哪扇门不该替用户开。**

打卡闭环：用户在「训练」页看完计划摘要（标题、理由、时长、热量、恢复分）和动作详情（肌群、器械、说明、wger 署名），点"完成并打卡"——`workout_logs` 写入一条 `source = 'ai_suggested'` 的记录，回写用过的 `exercise_ids`，顺手把首页缓存标记失效。这里要更正一个容易想当然的印象：**`exercise_ids` 列不是老早预留的，它就是这次随动作库一起加的**（`20260819_exercise_catalog.sql`，W4-T1）——建库、加列、回写，同一刀落成。

## 6.2 五个 Tab，和一个自找的坑

导航从「首页 / 记录 / 我的」变成「**首页 / 助手 / 训练 / 记录 / 我的**」。同时删掉两个重复入口：首页的"与 HOP 对话"大按钮、记录页的"今日训练计划"——Tab 里有的，别处不再摆第二份。

但这次改动顺手挖出一个坑。新 TabBar 组件（HomeTabBar.vue）的切换用的是 `uni.redirectTo`——它的特性是**销毁当前页、打开新页**。于是每次回首页，页面重新创建，内存清零，onShow 里的"拉晨报 + 全量刷新"全部重来一遍。用户的感觉就一个字：慢。

这个坑在 W4 里当周就填了一半（见 6.4 的缓存），另一半（改用原生 tabBar + switchTab，让页面真正常驻）排进了 W5。教训记在这：**redirectTo 适合"走完就别回头"的流程页（登录、引导），不适合当主框架用。** 主框架的五个 Tab，每次切换都不该付重建页面的税。

顺带记一个 P1 任务（T4）：手动记录的运动类型从早期的少数几种，扩到**约 19 种、带分类展示**——记录页和计划页的手动录入共用 `lib/health/workout.ts` 这一套定义。它不起眼，但"手动和 AI 用同一份运动字典"意味着：用户手记的羽毛球和计划里的羽毛球，在任何统计里都是同一种东西。**字典只有一份，是所有数据合并的前提。**

## 6.3 恢复分重写：三种冤枉的平反

恢复分是 HOP 的中枢数字——AI 的一切建议都围着它转。W2 版的它有四维：睡眠 40 + 休息 30 + 活动 20 + 心情 10。维度比例没动，W4 修的是三个冤案。

**冤案一：没有睡眠数据的人。** 旧规则下，无真实睡眠时要么拿 Mock 睡眠时长顶包（假数据冒充），要么睡眠维打 0（没戴表等于没睡？）。新规则：睡眠维给**中性分 32/40（80%）**，打上 `sleep_missing = true` 标记，首页文案直说——"睡眠数据缺失，恢复分仅供参考"。**不知道，就承认不知道，但别假装知道，也别惩罚不知道的人。**

**冤案二："练 7 休 2"的人。** 旧规则看"今天休息了没有"，训练日休息维 0 分——认真训练的人天天被扣分。新规则取两条路里较高的那条：① 连续无训练天数 × 10，封顶 30；② 近 7 天休息天数映射——休息 1 天得 22，休息 ≥2 天得 30（满分档）。数据来自真实的 `workout_logs`。按新规则，"练 7 休 2"的训练日休息维是 30，不再是 0。**休息不是"今天没练"，是"最近有没有安排休息"——指标的时间窗变了，冤案就翻案了。**

**冤案三：心情被代表的人。** 旧规则心情维写死 normal——按 W2 当时的公式，四档是 great 10 / good 7.5 / normal 5 / tired 2.5，所以**所有人每天都拿同一个 5 分**，App 根本不问。新规则：新增 `mood_logs` 表，每日一条（user_id + date 唯一），四档心情重新定档——很好 great 10 / 不错 good 9 / 一般 normal 8 / 疲惫 tired 4——可选备注 200 字以内，近 7 天可删。没记录时仍回退 normal（在新档位下是 8 分）——宁可保守，不逼打卡。

工程上还有个值得抄的动作：恢复分逻辑抽成了共用模块 `supabase/functions/_shared/recovery.ts`——recovery-score 和 morning-brief 两个函数**共用同一份代码**。修复前，这两个函数各算各的，改一处忘一处是迟早的事。**同一件事的计算逻辑，物理上只允许存在一份。**

## 6.4 缓存与自动同步：赶走"昨天"的幽灵

「早上打开 App，看到的还是昨天的简报」——这只幽灵是怎么住进来的？两个原因叠加：首页只读云端、从不会主动从手机拉数据；App 跨日保活时，页面内存里的"今天"还是昨天。

**缓存（T7）的解法**，一个 Pinia store（`stores/home.ts`）按"用户 + 本地日期"保存首页快照，规则朴素：

- 快照 **5 分钟内新鲜**：直接秒开，不请求
- 过期但有快照：先给用户看旧数据，**静默刷新**在背后跑（简报只读库，不重新生成）
- 记录运动/睡眠/心情、或 HealthKit 同步后：`invalidateFresh` 标记失效
- **跨日或换用户：快照直接丢弃**（登出时 `home.clear()`）——幽灵的巢穴，一发现就拆

**自动同步（T8）的规则表**，四行说清：

| 场景 | 行为 |
|---|---|
| 进入首页/授权页 | 距上次同步 ≥ 30 分钟，或已跨本地日 → 自动拉 HealthKit 并上传 |
| 生成/刷新晨报 | **先强制同步**（60 秒内刚同步过则跳过，防连打两次） |
| 手动点刷新 | 立即同步 |
| 跨日 | 丢弃昨日缓存，再同步 |

第五章那句"W3 以手动刷新为主"在这里补完：**自动同步的三件套（半小时、跨日、晨报前），W4 全部到位。**

顺手修了一个时区 bug：sync-healthkit 在 payload 缺 date 时，原来按 UTC 算"今天"——而东八区的凌晨（比如 1:00），UTC 还是前一天。于是凌晨记的东西会被写进"昨天"。改成 **Asia/Shanghai 的今日**。**服务器没有时区概念，你的用户有。所有"今日"，都必须明确锚定时区。**

## 6.5 数据补齐：修好基础代谢，和一条"不读"的边界

第五章交代过：W3 的插件清单里写了基础代谢，实际没查。W4-T10 把它和一批类型一起补齐了。这里先摆一个对代码时的口径差异：**执行记录的对照表按行算是 15 行；`DEFAULT_READ_TYPES` 数组里是 16 个 identifier**——因为静息心率和平均心率在代码里拆成了两项。数数口径不同，都是同一批东西。另一个细节：浅睡/核心睡眠这类分段，多半不是新的授权类型，走的仍是 SleepAnalysis。

新增的类型包括：基础代谢（修好）、步行+跑步距离、爬楼、浅睡/核心睡眠、最高心率、步行心率、**HRV、血氧、呼吸频率、VO₂ Max**（最近一条，非仅今日）。

两个细节值得停一下。

**其一，重授权机制。** 读取类型扩了，但用户在 W3 授权时只批过旧清单——怎么办？代码里放了 `HEALTHKIT_READ_TYPES_VERSION = 2`：版本落后的用户，同步前会再走一遍 `requestAuthorization`，**系统只弹新增类型**，不用全部重来。用户需要在弹窗里全点允许。这个"版本号驱动重授权"的招数，任何读系统权限的 App 都用得上。

**其二，故意不读的东西。** 病历、化验、用药、经期、饮食日记——HealthKit 里都有，HOP **一个都不读**。原则一句话：只读"活动 / 睡眠 / 心肺恢复"里用得上的，临床数据一律不碰。**一个健康 App 的隐私边界，最好写在"它拒绝读什么"上。** 顺带，无 Apple Watch 的用户 HRV/血氧/VO₂ 显示"--"属正常——不是 Bug，是你的设备没长那个传感器。

工程提醒（W4 用一晚上换来的）：改了 Swift/UTS 代码，**自定义基座必须重打**，标准基座无效；数据库侧，`20260821_healthkit_recovery_metrics.sql` 给 daily_summaries 加了 7 个新列（最高心率、步行心率、hrv_ms、spo2、呼吸频率、爬楼、VO₂）；manifest 的 `NSHealthShareUsageDescription` 隐私文案同步更新——**权限清单变了，跟用户的解释也要跟着变，这是审核的红线。**

## 6.6 证书踩坑：第五章预告的兑现

W4-T11，一个 P2 优先级的任务，内容是"记录一次踩坑"——是的，踩坑本身被排进了任务表。

现象：HBuilderX（Windows）重打自定义基座后，真机安装失败。排查时先后排除掉两个嫌疑：不是删掉手机上 TestFlight 包引起的，版本（约 0.3.8 / versionCode 138）也对过。根因：云打包制作自定义调试基座时，**选成了 TestFlight 用的发布证书**。规则表：

| 场景 | 证书 |
|---|---|
| USB 自定义调试基座 | iOS Development + Development profile（含本机 UDID） |
| TestFlight / 上架 | Distribution + App Store profile（不需要 UDID） |

改回开发证书重打，恢复。这条教训第五章已经预告过一句（"两套证书搞混，打包环节能折腾掉你一晚上"），这里给它正名：**那"一晚上"真实存在，日期 2026-08-21，还领了自己的任务编号。** 在这个项目里，踩过的坑不是聊天记录，是有编号、有表格、有修复记录的资产。

## 6.7 没做的清单：W4 的另一半成绩

W4 做了很多，但这一节想说的是**没做的**。这些每一条都是原计划里有过、W4 明确放掉的：

- **Sleep Insight Agent**（睡眠洞察）——不做，理由：先保证睡眠数据能稳定进来、缺数据时恢复分不误导，再谈洞察
- **Weekly Review Agent**（周报）——不做，理由：日闭环（计划→打卡→心情→晨报）还没转完整，周报是空中楼阁
- **微信支付/订阅**——不做，仍在免费内测
- **公开测试扩面**——不做，理由一行字：**先修同步、导航、说明书**

第五章结尾说过：那张空着的反馈表，没有排进 W4 的第一优先——因为真数据暴露出来的产品问题更急。W4 记录给这个决定留了官方注脚：扩面排在修完同步、导航、说明书**之后**。这不是逃避，是排序——**用户增长之前，先把已有用户会撞上的墙拆了；在墙上开窗之前，别急着请更多人来看。**

顺延不等于丢弃：原生 tabBar、Sleep Insight、Weekly Review、血压等生活方式指标、种子扩面、支付、上架材料——全部进了 W5 候选清单。**砍掉的任务最好也有一张清单，因为它记录的是"什么时候、为什么"放下的——未来的你会回来查。**

## 6.8 里程碑与账本：P0 九项，和一个分项的空缺

验收先说结果，按官方清单的口径：

**P0 九项全过：** 动作库可同步且 Agent 只用 featured；计划可生成、可看详情、可打卡；五 Tab 全通；心情入分；缺睡眠中性分 + 提示；首页 5 分钟缓存；自动同步三件套；HealthKit 扩展类型真机生效（8-21 验证）；**sync-healthkit / recovery 相关 SQL 已在目标项目执行**——这最后一项看着不起眼，但它是前八项的地基：migration 没跑，新表新列都是空中楼阁。

**P1 两项全过：** 说明书 v1.1（MD + PDF）；T4 运动类型约 19 种扩容。

**P2：** 证书踩坑记录（T11）——已完成，见 6.6。

工程上，这是四周以来**最干净的一次验收**——没有一项打折扣，没有一项靠"降低标准"通过。

然后是账本，这里要把"缺"和"有"说精确。W4 的执行记录里只有任务、日期和验收勾——**没有逐任务的工时分项**。但整周的数字不是没有：开发回顾里有合计——**净投入约 25 小时、AI 参与度约 72%**（表里多数任务标"高"，缓存和自动同步标"中"）、日历记 1.5 周。所以正确的说法是：**整周数字以回顾为准；缺的是 W2 那种"每个函数几小时"的分项账。** 宁缺的是分项，不是整周——硬编一条"动作库 4 小时"式的假明细，比空着更有害。

把四周连起来看：净投入 8h → 17h → 21h → 25h，逐周走高，25 小时是曲线的自然延伸；AI 参与度 72% 基本持平。全项目到 W4 为止：**6.5 周、约 71 小时、AI 平均约 73%。**

W4 结束时的 App 长这样（版本约 0.3.8）：五个 Tab；AI 每天从 160 个精选动作里出计划，用户打卡，打卡改变休息平衡，休息平衡影响恢复分，恢复分决定明天计划的强度——**一个闭环第一次真正转了起来**；心率、血氧、HRV 在有手表的用户手机里静静躺着；说明书 v1.1 跟上了功能面。它离"能拿给陌生人用"，只差一次真正的扩面。

## 常见问题

**Q：为什么要自建动作库，直接让 LLM 出动作名不行吗？**
不行，两层原因。第一层是安全：LLM 编出来的动作可能不存在、不适合、甚至危险——"只许选 ID、禁止编造"这条规则，等于把 AI 的创造力圈在了围栏里；而且围栏比很多人想象的更窄：**库里 860 条，出题只用约 160 条 featured 精选**。第二层是稳定：同一个"恢复分 60、想练下肢"的用户，今天和明天拿到的动作池是同一批——**AI 负责编排，不负责发明**。这套"围栏 + 排列组合"的思路，可以平移到任何"AI 出内容"的场景：菜谱、旅行计划、学习清单。

**Q：恢复分规则改了，历史数据的分数怎么办？**
先看存储方式：每次计算出的恢复分会写入 `daily_summaries.ai_recovery_score`，是个入库的快照。所以规则改后的实际行为是：**新一次计算（新一天的晨报）走新公式；库里已有的历史行不会自动重算**，除非重新生成。副作用是用户翻到上周的分数，看到的仍是旧规则下的快照。HOP 接受了这一点，因为旧规则本身是错的——**错误的连续性，不值得维持；但已写下的数字，也不必连夜涂改。**

**Q：缓存 5 分钟会不会让用户看到旧数据？**
会有 5 分钟内的旧窗口，但换来的首页秒开。而且缓存失效点铺得很密：记录运动/睡眠/心情、HealthKit 同步、手动刷新，任何一件发生都立刻作废缓存。**缓存的正确姿势不是"存多久"，而是"谁有权让它立刻失效"。** 想清楚失效点，新鲜度和速度可以兼得。

**Q：我的 App 不涉及健康数据，6.5 那节有什么可抄的？**
三样东西跨领域：**版本号驱动的重授权**（权限需求变了，只增量请求新增项，用户不会被重弹一遍全部）；**"故意不读"清单**（隐私边界写在拒绝项上，比写在隐私政策里有说服力）；**改了原生代码必须重打基座/重发包**（CI 环境同理——构建产物的版本对不上测试对象，测了个寂寞）。

**Q：W4 的账没有分项，这个系列的账还可信吗？**
可信，但要说清楚可信在哪一层：整周数字（约 25h、AI 约 72%）来自开发回顾的合计，是账；逐任务分项，W4 没记，就没有。这个系列教的从来不是"AI 参与度该是多少"，而是"账要怎么记才可信"——**有合计记合计，有分项记分项，缺哪层就承认缺哪层，不拿编的补。**

---

第四周结束——按日历说，是第十二天结束——HOP 第一次拥有一个完整转动的闭环：数据进来，分数算出，计划生成，打卡回写，明天的分数因此不同。AI 在这个环里干的活，从"说漂亮话"变成了"围着围栏做排列组合"；人干的活，从"审代码"变成了"定边界"——哪些数据不读、哪些重量不给、哪些 Agent 先不做。

但环转起来之后，最大的问题变了：**它只在开发者自己的手机上转。** 扩面还没有发生，那张反馈追踪表至今仍是空模板——第五周要还的债不是代码，是"发出去"这个动作。

而这一周的记录里还埋着一颗没爆的雷：TabBar 的 redirectTo 换成原生 tabBar + switchTab，被写进了 W5 候选清单的第一行。换导航框架这种事，牵一发动全身——下一周见。
