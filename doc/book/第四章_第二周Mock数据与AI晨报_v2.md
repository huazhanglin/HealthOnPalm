# 第四章 第二周：假数据与第一份晨报

第三章结束时我说过一句话：这一周做的所有决定里，最重要的一个是"先造假数据"。这一章就讲它——以及围绕它展开的一整个 AI 功能周。

W2 的目标只有一句话：**跑通 Morning Brief Agent，让用户每天早上收到 AI 健康简报。** 听起来是"一个功能"，拆开是十一个模块：Mock 数据服务、恢复分计算、晨报 Agent、问答 Agent、训练 Agent、安全 Agent、记忆 Agent、对话界面、Edge Functions 部署、定时推送、集成测试。

这一周结束时，我的 App 第一次"活"了：打开首页，AI 会基于你的身体状态说一段人话；进入对话页，你可以问它"我最近睡得好不好"。而支撑这一切的健康数据——步数、睡眠、心率——**全是假的**。

这不是作弊，是这一章最想教给你的一课。

## 4.1 先造假数据：为什么这是对的决定

W2 开工前，面前摆着一个选择：先接 iOS 的真实健康数据（HealthKit），还是先造假数据跑通 AI 链路？

龙虾的规划是后者，理由值得展开讲：

**第一，依赖解耦。** HealthKit 授权、数据读取、格式转换，每一个都可能卡住你——权限弹窗被拒、字段对不上、单位换算出错。如果 AI 链路和真实数据绑在一起，任何一个环节卡壳，整条链路都动不了。先用假数据，AI 那头可以先跑。

**第二，问题隔离。** 假数据是"已知正确"的输入。晨报生成不对，问题一定在 AI 链路里，不用怀疑数据；等 W3 换上真实数据再出问题，就知道该往 HealthKit 那头查。调试的本质是排除变量，假数据就是那个被固定死的变量。

**第三，MVP 的顺序本来就该是"价值优先"。** 这个 App 的核心价值是"AI 每天给我说得准的建议"，不是"能读到我的步数"。先用假数据验证 AI 建议的质量，如果 AI 说的话不靠谱，接真实数据毫无意义——那才是最大的沉没成本。

Mock 数据服务本身是个 Edge Function（`mock-health-data`），生成逻辑颇有讲究——**不是乱造，是"按人设造"**：

| 字段 | 生成规则 |
|---|---|
| 步数 | 初级 3000–7000；中级 5000–11000；高级 8000–16000 |
| 睡眠总时长 | 用户目标 ±1.5 小时 |
| 深睡 / REM | 总时长的 15%–25% / 20%–30%，浅睡为剩余 |
| 睡眠质量 | （实际÷目标）×70 + 随机 0–30，夹在 0–100 |
| 活动卡路里 | 150–550 kcal |
| 站立时长 | 4–8 小时 |
| 静息心率 | 初级 65–80；中级 58–68；高级 52–62 |
| 心情 | great/good/normal/tired，权重 0.1/0.35/0.35/0.2 |
| 今日已运动 | 40% 概率为是 |

注意第一行和倒数第三行：**假数据的"人设"跟用户档案联动**。一个自称初级的用户，mock 出来的步数就是初级区间，静息心率也是初级水平。这样 AI 收到的上下文是自洽的——不会出现"每天走 15000 步的初学者"这种矛盾数据，测试才有意义。给 Cursor 的提示词里只需要说清"数据根据 fitness_level 自动调整"，它就能写出这组规则。

代码里还留了一行显眼的注释：**TODO：W3 替换为真实 HealthKit 数据。** 假数据不是权宜之计，是被明确标记了"保质期"的施工脚手架。

## 4.2 计划赶不上变化：OpenRouter 之死

讲正题之前，先讲 W2 开工部署时就撞上的墙——因为它是全书到目前为止最典型的一次"AI 帮不上忙"。

技术设计阶段，我们选的 LLM 入口是 OpenRouter（一个大模型聚合平台）。计划照做，代码照写，到 W2 真正部署调用时，才发现：**OpenRouter 在国内无法访问。**

最挫败的地方在于，这个问题 AI 提前发现不了——AI 的知识截止日期里，OpenRouter 活得好好的。它是基础设施问题，不是代码问题，AI 的答案全在模型参数里，参数里没有"此刻的墙"。这类盲区以后还会遇到：AI 能写代码，但不能操作图形界面；AI 能整理信息，但不擅长质疑信息。

解决方案是把 LLM 入口整体切到 **SiliconFlow（硅基流动）**：国内直连，API 格式与 OpenAI 兼容。改动看着不大，牵连不小：

- 对话模型路径：`openrouter/deepseek/deepseek-chat-v3` → `siliconflow/deepseek-ai/DeepSeek-V3`
- Embedding 模型：`text-embedding-3-small`（1536 维）→ `BAAI/bge-m3`（1024 维）
- 数据库：W1 建表时按原选型建的是 `VECTOR(1536)`，现在要执行 ALTER 改成 1024 维

最后一项最阴险。如果没发现维度不匹配，后面所有向量检索都会在运行时报错——而设计文档、建表 SQL、Edge Function 代码里写的全是 1536。整个切换花了半天：更新 W2 计划里所有配置参数，生成一份完整的"迁移清单"逐项核对。

教训只有一句话，但值钱：**开工前，先用最小代价验证基础设施的可用性——一个 curl 请求的事。** 设计文档再漂亮，也验证不了"现在、此地、这个网络"能不能访问。

## 4.3 恢复分：让 AI 建议有据可依的数字

晨报要回答的核心问题是"今天该练、轻度活动、还是休息"。让 AI 直接拍脑袋？不行——大模型没有稳定的标准，今天说练明天说休息，用户很快就不信了。所以需要一个**确定性的数字**：恢复分（Recovery Score），0 到 100，规则算出来，AI 只负责解释它。

W2 版的算法，四个部分加权：

| 组成 | 权重 | 逻辑 |
|---|---|---|
| 睡眠分 | 40 | min(40, 睡眠比例 × 30 + 睡眠质量分 ÷ 100 × 10)；睡眠比例 = 实际÷目标，上限 1.3——多睡不加分 |
| 休息日分 | 30 | 连续休息每天 +10，封顶 30；计划注释写明"今天已运动则归 0" |
| 活动量分 | 20 | 以 8000 步为基准，min(20, 步数比例 × 13.3)；步数比例上限 1.5 |
| 心情分 | 10 | great 10 / good 7.5 / normal 5 / tired 2.5 |

总分三档：**≥80 训练（train）；50–79 轻度（light）；<50 休息（rest）。**

这套算法不是拍脑袋，配了四个测试用例，而且是**先写测试再实现**：睡眠充足（8 小时、8000 步、心情不错）要拿到 70 分以上；只睡 3.5 小时、疲惫，必须压到 35 以下；连续休息两天加好睡眠，结论必须是 train；极度疲劳，结论必须是 rest。**给算法配测试用例，再让 AI 按用例实现**——这是"人主导、AI 执行"的标准姿势。

这里有个诚实得近乎好笑的细节：休息日分的设计里写着"今天已运动则归 0"，但当周晨报代码里，连续休息天数这个输入**写死为 0**——注释是"MVP 暂不计算"。也就是说，W2 的用户实际上永远拿不到休息日加分。没人发现？发现了，但不修。因为那个阶段的目标是链路转起来，不是数字完美。

坦白说，这一版算法整体都有粗糙之处：睡眠多睡是好事还是坏事（睡 10 小时未必比 8 小时好）、连续练三天该不该强制休息，这些"睡眠中性分""休息平衡"的精细规则，W4 才重做。W2 先跑通——**数字可以不准，但链路必须先转起来；数字后面随时可以调，链路断了什么都谈不上。**

## 4.4 晨报 Agent：一条完整的调用链

W2 真正的主角是 Morning Brief Agent。它是一个跑在 Supabase 上的 Edge Function（可以理解为"部署在云上的一个函数"），当周的主路径长这样：

```
读取用户档案（users 表）
  → 调 mock-health-data，拿到今日健康数据（TODO：W3 替换为 HealthKit）
  → 调 recovery-score，算出恢复分与训练建议
  → 组装 Prompt，调用 DeepSeek-V3 生成晨报文本
  → 本地拼接免责声明（当时的简化版：关键词过滤，Day 8 的 MVP 做法）
  → 写入 daily_summaries（upsert，含原始数据快照 context_snapshot）
  → 记录 token 消耗到 token_usage_logs
```

请注意这个"当周主路径"的措辞——它很重要。完整的 Safety Agent 和两层记忆（4.5、4.6 节的主角）是 W2 中后段才补上的，补上之后晨报函数里才有了正式的 `runSafetyCheck`。**功能是一条一条长出来的，不是一天齐装满员的**；对话路径（用户发问）更是另一条链：问句进来先过安全检查、带工作记忆、生成、再过一遍安全检查出去。两条链路职责不同，后面会分开讲。

这条链里有两个设计值得停下来讲。

**一是链式调用是预先设计好的。** 每个函数的接口规范、输入输出 Schema、Prompt 模板，都在执行计划文档里写好了，AI 是照图施工。事后回顾，这是 W2 执行几乎没走弯路的最大原因。回顾里的定性是：约 10 个 Edge Function，约 8 个由 AI 生成初稿、人工微调后部署——前提就是执行计划写清楚了。同样是让 AI 写代码，"你不懂、AI 也不懂"的场景下它会生成看起来对、跑起来错的代码；"你懂、它执行"的场景下又快又稳。**你在流程里的位置，决定 AI 的产出质量。**

**二是每次调用都留快照、记账。** 晨报入库时，把当日的健康数据、恢复分、生成时间一并存进 `context_snapshot` 字段；token 消耗记进 `token_usage_logs`。前者是为了事后能回答"那天 AI 为什么这么建议"（原始输入都在），后者是个人开发者的账本——AI 每说一句话都是钱，不记账，月底账单能吓你一跳。

生成晨报的 Prompt 分两层。系统提示词（system prompt）定人设，W2 计划稿里的原文如下：

```
你是 HOP，一位专业、温暖、简洁的个人健康教练。
你的特点：
- 简洁直接，不啰嗦
- 语言像朋友在说，不像医生
- 每天只给一个重点行动建议（不多贪）
- 结尾必须附注"以上为非医疗建议，如有不适请咨询医生"

禁止：
- 不提诊断、治疗、处方、药物推荐
- 不给具体重量/组数/次数建议
- 不制造焦虑
```

（一个后话：现行代码里这段 prompt 后来改过——免责声明不再写死在结尾，改由 Safety 层统一把关。上面记录的是 W2 当周的原貌，你要是去翻现在的代码，对不上是正常的。）

用户侧提示词（user prompt）则把档案、健康数据、恢复分填进模板，要求生成：温暖问候 + 今日关键词、一个重点行动建议、个性化理由、一个可立刻执行的操作——**最多 150 字**。

这个 system prompt 值得抄走的不只是格式。注意"每天只给一个重点"和三行禁止——健康 App 最容易犯的错是变成养生百科全书和焦虑制造机，这些约束就是在 Prompt 层面给 AI 划红线。**Prompt 就是 AI 员工的岗位职责说明书，写得越像法律条款，它越不容易闯祸。**

调用参数也交代一下：模型 `deepseek-ai/DeepSeek-V3`，max_tokens 800，temperature 0.7。temperature（温度）可以理解为"发挥程度"——0.7 是偏稳的常规值，健康建议不需要天马行空。

## 4.5 Safety Agent：给 AI 上的第一道闸

健康领域的 AI 有个绕不开的问题：用户会问医疗问题。"我可能得了高血压怎么办"——AI 若接话诊断，就是越界，甚至危险。

Safety Agent 的设计是两层审查。第一层是**规则引擎**——一堆正则表达式，毫秒级扫描文本，动作分三种：

- **BLOCK（拦截）**：命中诊断类用语（诊断、确诊、患有、得了）、药品、严重症状、精神危机、病名清单（高血压、糖尿病都在里面）等关键词，直接拒答，返回标准话术
- **REFER（转介）**：命中"一直疼""持续疼""流血""骨折"这类持续或严重表述，以及孕产、儿童老人相关话题——回复引导就医但不硬拒
- **ALLOW（放行）**：正常健康话题，正常回答

只有过了第一层，才进第二层 LLM 复查（用另一个提示词让模型按"是否含诊断/治疗/处方、是否可能制造焦虑"几个维度输出结构化判断）。MVP 阶段可以通过 `skip_llm_check` 参数跳过第二层——省 token；但有一条保底：**LLM 复查如果调用失败，保守起见按不安全处理**。宁可错杀，不可放行。

有人会问：正则拦关键词，也太原始了吧？恰恰相反，这是分寸感。**第一层便宜、快、确定；第二层贵、慢、聪明。** 高频流量用便宜的挡掉大部分，疑难杂症才用贵的。这个分层思路在工程里到处都是（缓存如此、风控如此），你以后设计任何 AI 产品都会用到。

Safety Agent 的测试用例，本身就是一份"坏人语录"，W2 计划里的原文长这样——

BLOCK 组："你可能患有高血压，建议服用降压药"；"根据你的症状，我诊断你可能有糖尿病"；"你应该去医院住院治疗"。

REFER 组："你最近一直头疼，应该去看医生"；"这个伤口需要缝合，建议去医院"。

ALLOW 组："有氧 30 分钟""睡前少看手机""疲劳多休息"。

集成清单里还有一条组合拳：**"我可能得了高血压"应被拦截**——这句话同时命中"得了"（诊断用语）和"高血压"（病名），两个字眼都够。可以看出，计划里备下的测试句都是第一层正则直接就能拦住的重话。那第一层有没有绕得过去的时候？有——比如用户说"我的血压有点高"，没凑齐任何一条诊断用语或完整病名，第一层确实可能放它过去。这正是第二层 LLM 复查存在的意义：语义理解是 LLM 的强项，绕过字面规则的软性表述，交给它兜底。

（另一个后话：现行代码后来又加厚了正则清单——"吃什么药""胸口""剧烈头痛"等都是后补的。本节记录的依然是 W2 当周的版本。）

## 4.6 Memory Agent：让 AI 记住你

没有记忆的 AI 每天都是失忆重启。HOP 的设计文档里画了四层记忆体系（工作记忆/情景记忆/语义记忆/程序记忆），但 MVP 只做前两层——又一次"先跑通再优化"。

**L1 工作记忆（memory-working）**：管"今天聊了什么"。存 conversations 表，按用户 + 日期一条；有两个硬参数写在代码里：`MAX_MESSAGES = 20`（历史超过 20 条就截断，只留最近 20 条）和 `SUMMARY_THRESHOLD = 12`（超过 12 轮自动触发一次 LLM 摘要，压缩成一段存在 `context_summary` 字段里）。为什么要压缩？因为每次调用 AI，历史对话都要作为上下文传过去——传 20 轮原文，token 成本爆炸；传一段摘要，几十个 token 就够。**记忆压缩的本质是省钱**，这和第一章建 `token_usage_logs` 是同一个动机。

**L2 情景记忆（memory-episodic）**：管"发生过什么事"。用户完成一次训练、连续坚持一百天，这类事件被转成向量（用 BGE-M3 模型）存进 `health_memories` 表，之后靠"语义相似度"检索——用户问"我之前练肩的时候什么感觉"，系统把这句话也转成向量，在表里找最接近的记忆。这就是 4.2 节那个向量列从 1536 维 ALTER 到 1024 维的用途，也是为什么维度不匹配会让整个记忆系统瘫痪。

两层记忆的分工，一个类比讲清：L1 是"今天聊天的草稿纸"，L2 是"你的人生大事记"。草稿纸每天换，大事记越攒越厚。

## 4.7 界面：晨报卡片与对话页

链路跑通后，剩两块界面收尾。

**首页晨报卡片**：恢复分用圆形进度条显示，颜色分档——绿色（≥80）、橙色（50–79）、灰色（<50）；配训练建议（💪 训练 / ☀️ 轻度 / 😴 休息）和简报正文。交互上有一条重要逻辑：**打开 App 先查今天有没有简报，有就直接读库，没有才调 AI 生成**——绝不重复调用，一个用户一天最多生成一次，token 就是钱。

**对话页**：类微信的聊天界面，用户消息绿底右对齐，AI 消息白底左对齐；输入上限 200 字，发送时显示 Loading；消息存 conversations 表，刷新不丢。对话的调用链也有记忆注入：发送前读工作记忆，收到回复后写回。首次打开显示欢迎语："你好！我是你的健康助手。有什么关于运动、睡眠、恢复的问题，随时问我～"

顺带一提计划与实际的出入：原计划对话界面写的是"类似微信"的样式，实际做成了独立聊天页；语音输入和语音播报是 W3 才加的。**计划文档是地图，不是铁轨**——这句话第三次出现了，以后还会出现。

## 4.8 被砍掉的定时推送

W2 计划里本来有一项：每天早上 7:30 定时生成简报并推送给用户。实际没做，而且砍得心安理得。

原因一：iOS/微信的推送都要走订阅授权，用户不点授权就推不了，为一个还不确定有人用的功能搭这套链路，不值。原因二：推送的本质是"替用户决定他什么时候看"，而 HOP 的场景是"用户打开时看到最新状态"——打开时生成，反而能拿到此刻的真实状态（比如今天已经运动过，简报跟着变）。

于是 W2 的最终形态是：**打开 App → 查今日简报 → 有就读、没有就现生成。** 少一个推送功能，多一份确定性。这不是偷懒，是又一次问了自己那句老话：这个阶段，值不值。

最后说说排期——这里有个容易写错的账。

**计划把整条 AI 链路塞进 7 个日历日，估时 43 小时；开发回顾却把 W2 记成了"两周"。而净投入，只有约 17 小时。**

日历拉长了，工时反而只有预估的四成——这不是赶工失败，是另一回事。把三本账摊开看：

- **净投入 17h** 对 **预估 43h**：是压缩，不是膨胀。预估偏松是一方面；更主要的是计划里的 T10 定时推送直接砍掉了（见 4.8 节），估时里它一分不少。
- **日历变长的原因，一条条可查**：一是 OpenRouter 切 SiliconFlow 发生在 W2 部署时——这是计划外的半天，改模型路径、改 Embedding 维度、回写计划配置；二是 W3 的 HealthKit 插件调研在 7 月 29 日就交了初版——那是 W2 的第 9 天，两条线在日历上叠着走，回顾却按"W2 两周、W3 两周"分开记账；三是 W1 计划本身写到 7 月 30 日，W2 从 7 月 28 日起算，两个"周"本来就不互斥。

所以 OPC（一个人 + AI 干活）的真实形状是：**晚上做一点、被基础设施打断、和下一阶段交叉。** 排期表上的"周"是地图，真实的工作像潮水，涨过线又退回来。如果你以后看到某个独立开发者的"两周做完一个功能"，先别急着自愧不如——去问问他日历里的净投入，多半比你想的少，也比他自己晒的少。

AI 参与度方面，回顾里的定性是约八成——十几个函数、上千行代码，绝大部分是 AI 生成初稿、我做微调和验收。我的时间花在哪了？花在写清楚每个函数的接口规范、Schema 和 Prompt 上。**这周再次验证了那个规律：你把文档写得多清楚，AI 就把代码写得多对。**

## 常见问题

**Q：用假数据开发，会不会最后忘了换成真的？**
不会，前提是你在代码里留下显眼的标记。HOP 的做法是在晨报函数里写死一行注释："TODO: W3 替换为真实 HealthKit 数据"——mock 调用旁边就是这句。替换点只有一个（链路的第 2 步），因为设计时就保证了 AI 链路只认"健康数据"这个接口，不关心它从哪来。**解耦做得好，换心脏不用换全身。**

**Q：恢复分为什么不直接让大模型算？**
确定性。同一份输入，代码算出来永远是一个数，大模型算出来每次都微妙不同。恢复分是全 App 的决策基准，基准不能抖。正确分工是：**规则算数字，AI 解释数字**——AI 负责把"74 分、轻度活动"翻译成人话并给出理由，这恰是它擅长的。

**Q：Safety 靠正则，用户换个说法不就绕过去了？**
部分绕得过去。比如"我的血压有点高"这种软性说法，可能凑不齐第一层的字面关键词——所以才有第二层 LLM 复查，语义理解是 LLM 的强项。MVP 阶段我用 `skip_llm_check` 关掉它是为了省 token，等用户量上来必须打开（现行代码的正则清单也已经加厚过一轮了）。**安全策略和恢复分一样：先跑通，再加固；但"先跑通"不等于"可以裸奔"，第一层正则从第一天就在。**

**Q：对话记忆只留 12 轮 + 摘要，会不会丢重要信息？**
会丢细节，保住要点。12 轮之前的原文被摘要替代，但重要事件（完成训练、受伤、里程碑）走的是 L2 情景记忆那条线，不依赖对话历史。这是分层的好处：**聊天记录可以廉价地压缩，人生大事单独建档。**

**Q：我做的不是健康 App，这套多 Agent 设计能抄吗？**
结构能抄，模块按你的领域换。通用骨架是：数据接入（可以先是 Mock）→ 确定性计算（你的领域指标）→ LLM 生成（人设写在 system prompt）→ 安全审查（你领域的红线关键词）→ 记忆（近期对话 + 长期事件两层）→ 落库记账。记账 App 就是：账单数据 → 月度结余 → AI 消费建议 → 防投资荐股拦截 → 消费习惯记忆。**领域会换，链路不变。**

**Q：我一周没做完计划，是不是失败了？**
先算两笔账再下结论：日历上过了几天，和实际净投入几小时。HOP 的 W2 日历上"变成两周"，净投入只有预估的四成——拉长它的是计划外的基础设施事故和跨阶段任务交叉，不是工时爆炸。**排期延误和产能不足是两种病**：前者的解药是把打断记录下来、下次给计划留缓冲；后者的解药才是砍需求。别把前者误诊成后者，砍掉本来做得完的东西。
