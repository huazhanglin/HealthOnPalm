# Health On Palm 开发过程回顾
## 一个普通开发者如何用 AI 工具「一个人做了一个团队的工作」

> **写作目的**：以 Health On Palm（HOP）项目为完整案例，记录从想法到 MVP 上线的全过程，整理 AI 辅助开发的方法论与工具链，供个人开发者参考。
>
> **时间跨度**：2026-07-17（项目启动）— 2026-08-07（W1/W2/W3 基本完成）
> **项目定位**：iOS 健康数据驱动的 AI 晨间简报应用（HBuilderX + Supabase + DeepSeek-V3）
>
> **2026-08-07 补充**：Auth 由手机号 OTP 改为 **邮箱+密码**；HOP 助手增加 **语音输入 / TTS 播报**；种子分发规划为 **TestFlight**。详见 `W3 详细执行计划_MVP第三阶段.md`「中期变更」。

## 一、项目背景：一个想法是如何落地的

### 1.1 起点：可行性分析

HOP 项目的起点不是一个技术方案，而是一个商业假设：

> "用户每天早上打开手机，能不能看到一个专属的 AI 健康简报，基于他真实的运动、睡眠、心率数据，告诉他今天应该注意什么？"

这个假设需要验证。第一个介入的 AI 工具不是代码编辑器，而是**大语言模型本身**。

**具体做法**：
- 用 Qwen-Max 生成《可行性研究报告》的第一版（v3.0）
- 用 ChatGPT 生成第二版对比（v4.0）
- 两者合并人工修订为 v5.0（最终版）

**关键教训**：LLM 写的可行性报告天然带有乐观偏差——它会告诉你市场规模有多大、用户有多需要、竞争对手有多弱。**必须有人做"唱反调"的那个**。这份报告由人工审核时发现了财务数据过于乐观、估值单位缺失、国内竞品分析不足等问题。

### 1.2 技术选型：约束下的一次性决策

技术选型发生在正式开始写代码之前。HOP 的约束清单：

| 约束维度 | 内容 |
|---------|------|
| 预算 | 月均 ¥750 以内（LLM 成本 ¥200/月） |
| 团队 | 1人，无运维资源 |
| 平台 | iOS + 微信生态 |
| 时间 | MVP 4周，V1.0 8周 |

在约束下，架构设计做了两个"反直觉"的选择：

**选择一：不用微服务，用 Supabase 一体化。**  
传统团队做健康数据应用，可能会拆出用户服务、数据同步服务、AI 推理服务、通知服务……每个服务一套代码库 + CI/CD + K8s 部署台账。但一个人做微服务，运维成本会吃掉所有开发时间。Supabase 把数据库 + Auth + Edge Functions + 向量存储打包在一起，第一个 Edge Function 部署到生产环境只用了 3 分钟。

**选择二：不用 GPT-4，用 DeepSeek-V3。**  
GPT-4o 当时的价格是 DeepSeek-V3 的约 15 倍。HOP 的晨间简报不需要 GPT-4 的能力边界，DeepSeek-V3 在日常对话和结构化输出上完全够用。月成本从 ¥3000+ 降到 ¥200，这是可持续做下去的前提。

## 二、文档先行：为什么先写技术设计文档

### 2.1 第一版是怎么失败的

2026-07-22，项目启动了第一版技术设计文档。这份文档的问题不在于写得不好，而在于**它根本不是一份技术设计文档**。

它更像一份"目录"——30章的框架，每个章节只有标题，没有实质性内容。一个真正的技术设计文档应该告诉开发者：

- 数据库表结构是什么，字段类型是什么
- 两个服务之间怎么通信，协议是什么
- 一个 API 请求从收到到返回，经过哪些模块
- 如果某个模块挂了，降级策略是什么

第一版文档只回答了"我要做什么"，没有回答"怎么做"。

### 2.2 第二版的方法：需求→约束→方案

第二版（v2.0 OPC版）的方法完全不同。从一开始就明确了一个定位：

> **这份文档是架构师的决策记录，不是团队执行手册。**

每个技术决策都遵循同样的结构：

```
[约束] → [选项] → [决策] → [代价/权衡]
```

举例：为什么选 LangGraph 而不用 LangChain？

```
[约束] 需要在 Edge Function 内运行，内存受限，不能跑重型运行时
[选项] LangChain / LangGraph / 纯手写状态机
[决策] LangGraph 轻量版
[代价] 需要自己封装 Supabase 的工具函数，没有 LangChain 的生态
```

这种方式让每个决策都是可追溯的。如果三个月后发现 LangGraph 不合适，回看文档能直接找到当时做决策的理由。

### 2.3 执行计划：把文档变成每日任务

技术设计文档是"地图"，执行计划是"行程表"。

W1 执行计划（34KB）包含了 Day 1-7 每天的具体任务：

```
Day 1（0.5h）：注册 SiliconFlow，充值 ¥10
Day 1（1h）：  Supabase 项目初始化，配置 .env.local
Day 2-3（3h）：Supabase Auth + 用户注册登录流程
Day 4（1.5h）：数据库 Schema 创建（按技术文档第 8 章）
……
```

每项任务后面跟着**验收标准**：怎么知道这件事做完了？

```
✅ Supabase Auth 集成验收标准：
- [ ] 用户注册邮箱收到验证邮件
- [ ] 登录成功后 token 写入 localStorage
- [ ] 未登录用户访问 /home 重定向到 /login
```

这个格式来自 AI 生成的初稿，但每一条验收标准都经过人工审核——因为 AI 不知道你用的是 Supabase Auth 还是自建 Auth，不知道 RLS 策略怎么配置。

## 三、AI 协同工作流：从"AI 写代码"到"AI 改代码"

### 3.1 AI 写代码的两种用法

用 AI 写代码有两种截然不同的场景，效果也完全不同：

**场景 A：全新领域，你不懂，AI 也不确定**
→ AI 输出的是看起来正确但可能有隐藏 bug 的代码
→ **典型案例**：第一版技术设计文档里写的 Edge Function 代码，逻辑看起来通顺，但部署到 Supabase 时发现缺少 CORS 头

**场景 B：有明确规范的已有领域，你指导，AI 执行**
→ AI 在约束内生成，速度极快，质量稳定
→ **典型案例**：HOP 的 Edge Functions（morning-brief、memory-episodic、query-agent 等），都是在 W2 执行计划里写清了接口规范、Schema、Prompt 之后，让 Cursor AI Agent 生成代码

关键区别在于：**人在流程中的位置**。场景 A 是"AI 主导，人审核"，场景 B 是"人主导，AI 执行"。

### 3.2 约束工具：agent.md

项目根目录的 `agent.md` 是整个 AI 协同的核心。它告诉每个 AI 会话：

- 项目是什么（Health On Palm）
- 当前阶段是什么（现在是 W3 阶段）
- 当前在做什么（HealthKit 数据同步）
- 边界在哪里（❌ 不做：微信支付、Kubernetes、PostgreSQL 以外的数据库）
- 技术栈是什么（Supabase + Deno + SiliconFlow + DeepSeek-V3）

当 AI 违反约束时，这个文件就是"纠正依据"。比如某个 AI Session 生成了接入 OpenAI 的代码，可以直接说"看 agent.md 第 4 条，不接第三方 LLM"。

### 3.3 Cursor 的多 Agent 协作

Cursor 是 HOP 的主要代码编辑器，它的 AI 功能不是单一的"chat"，而是可以针对不同任务开不同的 Agent Session：

| Agent 用途 | Session 名称约定 | 典型任务 |
|-----------|----------------|---------|
| 代码生成 | `cursor-session-W3-T2` | 生成 HealthKit 授权页 UI |
| 代码审查 | `cursor-review-W3` | 检查 Edge Function 是否有 SQL 注入 |
| 技术调研 | `cursor-research-T1` | HealthKit 插件市场调研 |
| 文档生成 | `cursor-doc-W3` | 生成 W3-T1 调研报告 |

多 Session 的问题是"上下文碎片化"——一个 Session 改了代码，另一个 Session 不知道。HOP 的解决方法是：

```
Session A 生成代码 → 人工把关键代码粘贴到文档注释 → Session B 读取文档
```

这不是最优解，但在一个人的项目里，这个成本是可接受的。

## 四、关键决策回顾：什么时候推翻了 AI 的建议

### 4.1 推翻点一：微信小程序 vs iOS App

AI 调研报告（Cursor + DCloud 市场插件调研）的最初结论是：用 DCloud 的 `szy-healthkit` 插件，可以在微信小程序里读取健康数据。

这个结论有一个根本性的问题：**微信小程序根本不支持 HealthKit**。iOS 的 HealthKit 是 Apple 的私有 API，只在 iOS App 里可用。微信小程序运行在微信的容器里，拿不到 HealthKit 的数据。

发现这个问题的是人，不是 AI。原因是：AI 在调研插件市场时，只看了插件的功能描述，没有验证"微信小程序能否访问 HealthKit"这个前置条件的真实性。

**教训**：AI 擅长整理信息，但擅长"相信"信息。当你需要质疑一个前提假设时，AI 的置信度和一个新手的置信度是一样的。

### 4.2 推翻点二：第三方插件 vs 自研 UTS

第一次推翻后，换成了 DCloud 官方插件路线。但 Cursor 的调研又发现了新问题：现有插件存在以下问题：

- 更新频率低（部分插件 1-2 年没更新）
- 不支持睡眠分段（iOS 16+ 的深睡/REM/清醒）
- 授权流程和国内隐私政策不兼容

最终选择：**自研 UTS 插件**。用 Swift 写原生 HealthKit 读取层，用 UTS 封装接口，H5/Android 用 stub 降级。这个决策推翻了 AI 最初"优先使用现成插件"的建议，理由是"自研的维护可控性远高于第三方插件"。

Cursor 实际执行了插件开发，最终交付了：

- `HealthKitBridge.swift`（原生读取层）
- `index.uts`（UTS 导出封装）
- `UTS.entitlements`（HealthKit Capability）
- `src/lib/healthkit/index.ts`（业务适配层）

### 4.3 推翻点三：OpenRouter vs SiliconFlow

项目设计阶段用的是 OpenRouter 作为 LLM 聚合 API。但到了真正部署时发现：**OpenRouter 在国内无法访问**。

这个是基础设施问题，AI 给不出解决方案——因为 AI 的知识截止日期里，OpenRouter 还活着。

解决方案是切换到 SiliconFlow（硅基流动），国内直连，API 格式与 OpenAI 兼容。DeepSeek-V3 的模型路径从 `openrouter/deepseek/deepseek-chat-v3` 改为 `siliconflow/deepseek-ai/DeepSeek-V3`，Embedding 模型从 `text-embedding-3-small`（1536维）改为 `BAAI/bge-m3`（1024维）。

这次切换花了半天时间，更新了 W2 执行计划里所有配置参数，并生成了完整的"迁移清单"。

## 六、AI 协同的四种模式

回顾整个 HOP 开发过程，AI 在项目中扮演了四种不同的角色，对应四种不同的协作模式：

### 模式一：AI 是"实习生"——执行明确的任务

**典型场景**：生成 W2 执行计划里的 Edge Function 代码。需求明确、接口清晰、约束具体。

**工作流**：

```
人：写清楚需求文档（含接口定义、Schema、验收标准）
  ↓
AI：根据文档生成代码
  ↓
人：审核代码，运行测试
  ↓
有 bug → 把错误信息粘贴回 AI → AI 修复
```

**效果**：这个模式下 AI 的输出质量最高，因为它在"执行"而非"决策"。HOP 的 Edge Functions（morning-brief、safety-check、recovery-score 等）大部分是在这个模式下生成的。

### 模式二：AI 是"顾问"——提供专业领域知识

**典型场景**：HealthKit 技术调研。让 Cursor Agent 研究 DCloud 插件市场，对比 3-5 个插件的优劣，给出推荐方案。

**工作流**：

```
人：提出问题（"iOS 健康数据读取有哪些方案？"）
  ↓
AI：整理信息，给出选项列表
  ↓
人：做决策（选哪个方案）
  ↓
AI：执行被选中的方案
```

**效果**：这个模式下 AI 的输出是"原材料"，人的判断是"筛选器"。AI 给出的选项里可能包含错误信息（比如"微信小程序可以读 HealthKit"），所以**每个选项都需要人工核实前提假设**。

### 模式三：AI 是"编辑器"——修改和完善人的想法

**典型场景**：把项目名从"Health Agent"改成"Health On Palm"（HOP）。

不是让 AI 决定叫什么名字，而是人决定了名字之后，让 AI 在所有文档里做批量替换和一致性检查。

**工作流**：

```
人：做出决策（改名 HOP）
  ↓
AI：扫描所有相关文件，执行替换
  ↓
验证：确认零残留
  ↓
AI：同步更新 UI 文案
```

**效果**：这种"人决策、AI 执行"的模式效率极高。一次改名涉及 5 个文档文件 + 2 个代码文件，手动改需要半小时，AI 批量处理 5 分钟完成，残留检查自动完成。

### 模式四：AI 是"镜子"——帮助人反思和优化

**典型场景**：代码审查、技术设计文档审核。

让另一个 AI Session 来审查主 Session 生成的代码，发现人容易忽略的问题。

```
主 AI：生成 W3 T3.1 Edge Function 代码
  ↓
审查 AI：读取代码，发现潜在的 SQL 注入风险
  ↓
主 AI：根据审查意见修改代码
```

**效果**：这个模式的价值在于"盲点检测"。人写代码时会形成惯性思维，AI 审查往往能找到明显但被忽略的问题。

## 七、W1 → W2 → W3：三个阶段的实际工作量

### 7.1 W1：基础设施搭建（1周）

**目标**：让 App 能跑起来，用户能注册登录。

| 任务 | 实际耗时 | AI 参与度 |
|------|---------|----------|
| Supabase 项目初始化 | 0.5h | 低（手动配置） |
| 数据库 Schema 创建 | 1h | 高（AI 生成 SQL） |
| Supabase Auth + 用户注册登录 | 3h | 高（AI 生成 Vue 页面） |
| Edge Function 脚手架 | 1h | 高 |
| RLS 策略配置 | 1h | 中（AI 建议 + 人工审核） |
| SiliconFlow 接入 + BGE-M3 Embedding | 1.5h | 高 |
| **W1 合计** | **~8h** | **约 70%** |

**W1 的最大挑战不是写代码，是配置**：Supabase 的 Auth 回调配置、RLS 策略、CORS 设置，每一项都需要在 Web UI 里手动操作，AI 帮不上太多忙。这是"AI 辅助开发"的一个盲区——AI 能写代码，但不能操作图形界面。

### 7.2 W2：AI 功能上线（2周）

**目标**：跑通 Morning Brief Agent，让用户每天早上收到 AI 健康简报。

| 任务 | 实际耗时 | AI 参与度 |
|------|---------|----------|
| morning-brief Edge Function | 3h | 高 |
| memory-episodic Edge Function | 3h | 高 |
| memory-working Edge Function | 2h | 高 |
| query-agent Edge Function | 2h | 高 |
| safety-check Edge Function | 1.5h | 高 |
| recovery-score Edge Function | 1.5h | 高 |
| SiliconFlow 接入 + BGE-M3 向量维度切换 | 2h | 高 |
| 每日简报推送 UI | 2h | 高 |
| W2 合计 | **~17h** | **约 80%** |

**W2 的特点**：代码量大，但每个函数的逻辑相对清晰。AI 生成 Edge Function 代码的效率远高于手写，10 个函数里 8 个是 AI 生成初稿、人工微调后部署的。

**一个意外发现**：Edge Function 之间的调用链很重要。`morning-brief` 需要先调用 `memory-episodic` 读取历史，再调用 `safety-check` 验证安全，再生成简报。这个调用顺序是 W2 文档里预先设计好的，执行时几乎没有走弯路。

### 7.3 W3：真实数据接入（2周）

**目标**：接入 iOS HealthKit，用用户真实的健康数据替代 Mock 数据。

| 任务 | 实际耗时 | AI 参与度 |
|------|---------|----------|
| HealthKit 技术调研（Cursor） | 3h | 高 |
| 自研 UTS 插件开发（Cursor） | 8h | 高（实际 Cursor 完成） |
| sync-healthkit Edge Function | 3h | 高 |
| HealthKit 授权 UI | 2h | 高 |
| 运动数据全面接入（跑步/游泳/羽毛球等）| 2h | 中（人提出需求，AI 扩展代码） |
| 种子用户内测 SOP | 3h | 中 |
| W3 合计 | **~21h** | **约 70%** |

**W3 的转折点**：从第三方插件改成自研 UTS 插件。这个决策浪费了约 3 小时（调研 + 初版文档），但换来了完全可控的技术栈。如果用第三方插件，后续 HealthKit API 变更时只能等插件更新；自研插件可以随时修改。

时间成本里没有完全体现的是**决策时间**：

## 九、关键方法论：一个人做项目团队的活的最小工具集

### 9.1 工具选择的三原则

**原则一：能一键部署的，不用需要运维的。**  
Supabase 替代了 PostgreSQL + Redis + 一个 Web Server。Vercel/Supabase Edge Functions 替代了 EC2。这让一个人的精力全部投入在"写代码"而非"管服务器"上。

**原则二：AI 能写的，不自己做。**  
Edge Function 代码、数据库 Schema、测试用例、文档初稿——这些 AI 写得出来，而且速度比人快 5-10 倍。人的时间应该花在：审核 AI 输出、做技术决策、测试 AI 跑不通的部分。

**原则三：最重要的文档是约束清单，不是功能列表。**  
`agent.md` 之所以重要，不是因为它写了 HOP 要做什么，而是它写了 HOP **不做什么**。AI 的本能是"尽可能满足需求"，当需求之间冲突时，AI 需要一个明确的约束来判断优先级。

### 9.2 AI 协同的最小工作流

```
每日开始：
  1. 读 agent.md（明确当前阶段和边界）
  2. 读当日 WX 执行计划（明确今日任务）
  3. AI 生成代码 / 文档初稿
  4. 人工审核（重点：边界条件、错误处理、隐私合规）
  5. 部署 / 测试
  6. 更新执行计划（标记完成 / 记录阻塞）

遇到决策点：
  1. AI 给出选项列表（不做决策，只整理信息）
  2. 人做决策（基于约束清单和长期目标）
  3. AI 执行被选中的方案
```

### 9.3 最容易踩的三个坑

**坑一：让 AI 替你做决策，然后为 AI 的决策背锅。**  
当 AI 说"用这个插件"、"用这个模型"、"用这个架构"时，记住：做决策的是你，承担责任的还是你。在采纳 AI 建议之前，至少问自己三个问题：这个建议的前提假设是什么？这个建议的失败模式是什么？如果错了，我的退路是什么？

**坑二：让 AI 写代码，但没有验收标准。**  
AI 生成代码的常见问题是"看起来对，跑了不对"。原因是没有验收标准，AI 的目标函数是"生成看起来合理的代码"，而不是"通过测试的代码"。**每段 AI 生成的代码，都应该有明确的验收标准**。

**坑三：多个 AI Session 各做各的，最后发现上下文不一致。**  
Cursor 的不同 Session、不同的 AI Chat 工具，它们之间不会自动同步状态。最容易出问题的场景是：一个 Session 改了 API 接口，另一个 Session 不知道，还在用旧的接口定义。**约束文档和执行计划是最好的上下文同步工具**——把所有 Session 共享的上下文写在那里，而不是写在某个 Session 的聊天记录里。
